§9, `phase4/ERROR_HANDLING.md` §Layer 8. Score honest per `phase5/CONSTRAINTS.md` instruction: a risk
already mitigated by shipped code gets a **low residual**, not a low likelihood - the underlying
condition (no cross-repo test, structural mutation-testing trap, local-only git hook config) stays
exactly as likely to recur elsewhere as before the one instance was fixed.

  for hosting and `ADR-038` for commerce. ⚠️ **The residual is unchanged and is not eliminated**: still a
  hand copy onto each of the six services and the seed, still no escrow, still nothing that compares the
  value before a deploy. The boot gate — `KEYGRIP_KEK_MISMATCH` and `exit 1` before the port binds —

  operated as a real production deployment by the platform owner, or if an adopter reports the documented

  (`COMPANY_LEGAL_ENTITY.md` §6), which is why this bullet carries no `R…` row: the two-writer race on `company` was
  recorded only as that epic's open question and never scored here. `ShopOwner` and `Admin` both write the
  card in one whole-object `$set`, so what is accepted is **whole-card** last-write-wins — the losing save
  reverts every field the other writer changed since its form loaded, not only the field both touched. No
  version, lock or precondition is planned; adding one reverses this decision. Bounded by what the payload
  cannot carry: `_id`, `idShopOwner` and `deleted` are outside both update types, so a race cannot reassign
  an owner (**R30**) or resurrect a retired company — and ⚠️ **`published` joined that list later the same
  day**, when publishing became `companyUpdatePublished` on both tiers, so a lost save reverts the card and
  never the shop's visibility. Reopening trigger: any flow where two writers
  routinely hold the same card open, or any field on `company` whose silent revert is worse than a re-edit.
- **R29 - `item.published` too, decided separately the same day.** An admin unpublishes, the owner
  publishes it again, and that is an accepted outcome rather than a defect. Asked as its own question
  because the cost is not the cost of the `company` race — a reverted `description` is a re-edit, a
  reverted unpublish is a failed takedown — and answered the same way. ⚠️ **Exactly two moderators, and no wider**: publishing is
  its own mutation on both tiers and `published` is in no input object, so an owner's save of another
  field cannot restore their own value of the flag without touching it.
  Nothing records that an admin flipped it either; there is no moderation log and
  none is planned. **`itemDel` is the admin action that survives an owner's save** — `deleted` is
  outside every input. Revisit only for a takedown the owner cannot undo, which is a second field or an
  audit trail, never a lock.
- **Qodana `SKIP_QODANA=1` escape hatch.** Exists platform-wide for any repo missing a `QODANA_TOKEN` or a
  Cloud project. Accepted as a documented bypass, not a silent one - both `.githooks/pre-commit` and
  `pre-push` still gate coverage and mutation score even when this fires. As of 2026-08-27 no repo
  depends on it: all fifteen are provisioned (R38), so it is a one-shot admin bypass rather than any
  repo's normal commit path.
