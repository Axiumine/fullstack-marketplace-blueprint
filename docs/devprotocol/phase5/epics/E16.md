## 1. Epic goal

Make the refresh-cookie signing key rotatable while the platform is running, without ever printing it. Today
the key lives in an env var, is read once at process boot, and has therefore never been rotated —
`RISK_REGISTER` R02 has recorded that as accepted risk since Phase 3. Keygrip's whole design is a *keyring*:
`sign` uses `keys[0]` and `verify` walks the rest, so a rotation costs nothing at verify time and only needs
somewhere to keep more than one key. This epic gives it that somewhere — a CSFLE-encrypted collection, a
lifecycle with three states, and a snapshot the running processes refresh on their own.

> **The goal above is met; the two clauses after the dash are not what shipped.** ADR-034 put the keys in one
> wrapped Redis record rather than a Mongo collection, and replaced the three-state lifecycle with an ordered
> list — index 0 signs, the rest verify, and a retirement removes an entry. The third clause survived intact:
> the running processes do refresh on their own. Read §3 and the per-story **Outcome** paragraphs for what
> that swap cost and what it bought; §2's table is kept as written, with the substitution marked per row.

## 2. Scope

| Item | In/Out | Why |
|---|---|---|
| `signingKey` collection, its migration and its DEK | In | key material must be encrypted at rest like every other secret field (ADR-029) |
| A key lifecycle: `current` → `verifiable` → `retired` | In | the three states Keygrip's sign/verify split already implies |
| An in-process keyring snapshot with a refresh interval | In | the actual fix for "keys frozen at boot" |
| `rotate()` and `forceRetire()` domain operations | In | rotation with no operation to invoke it is R02 unchanged |
| The bootstrap path for a database with no keys yet | In | the platform must still start on a fresh install |
| Removing the Keygrip env var, and the env-count correction it forces | In | leaving both sources live is worse than either alone |
| Any UI | Out | E17 — this epic ships the domain and the GraphQL surface, not the screen |
| Returning, logging or displaying key material anywhere | **Explicitly out, permanently** | see the constraint below |
| Rotating the CSFLE master key or any DEK | Out | ADR-029's own problem, not this one |

**What each In row became (v2.0).** The table is kept as written — it is the record of what was asked for.

| Row as written | What shipped |
|---|---|
| `signingKey` collection, its migration and its DEK | one AES-256-GCM-wrapped Redis record at `<REDIS_KEY>keygrip`, unwrapped with `KEYGRIP_KEK`, version as AAD. No collection, no migration, no fifth DEK (ADR-034) |
| lifecycle `current` → `verifiable` → `retired` | an **ordered list**: index 0 signs, every later entry verifies, a retirement removes an entry. The states are positions, not a field |
| in-process snapshot with a refresh interval | `watchKeygrip` — a pub/sub nudge with a `KEYGRIP_POLL_MS = 300_000` fallback. Measured at 37 ms, not at the interval (E16-S09) |
| `rotate()` and `forceRetire()` | `keygripRotate` and `keygripRetire`, Admin GraphQL mutations rather than domain functions called by something else |
| bootstrap for a database with no keys | `seedKeygripRecord` in `marketplace-db-setup/lib/keygrip.js`, idempotent, run against Redis rather than Mongo |
| removing the Keygrip env var | `KEYGRIP_KEY_1`/`_2` gone from five `env` templates, five `REQUIRED_ENV_VARS` and `src/**` behind an eslint ban (E01-S15) |

The two Out rows and the permanent one are unchanged and were honoured: no UI shipped here, no DEK was
rotated, and nothing on the GraphQL surface can carry key material.

> **Hard constraint on everything below.** No resolver, log line, error message, test fixture snapshot or
> admin response may contain a signing key, a substring of one, or a prefix of one. Key material moves
> between the collection and the keyring snapshot and nowhere else. Every story that touches the GraphQL
> surface carries a mechanical check for this.

## 4. Stories

### E16-S01 — Signing keys live in an encrypted collection   `built`
**As a** platform operator, **when** the platform needs a signing key, **I want** it read from an encrypted
collection rather than an env var **so that** more than one key can exist at a time and a key can be added
without a redeploy.
**domains:** backend, database, testing
**Acceptance criteria:**
- A new migration in `marketplace-db-setup` creates a `signingKey` collection with a strict `$jsonSchema`
  carrying `additionalProperties: false`, shared from `lib/schemas/` like every other collection, with fields
  for the key material, a `state` enum of exactly `current` / `verifiable` / `retired`, a creation timestamp
  and a rotation timestamp
- The key-material field is registered for CSFLE with its own DEK via a new `KEY_ALT_NAMES` entry in
  `encryptedFields.mts`; a test asserts the entry exists and that the field is listed as encrypted
- A partial unique index guarantees **at most one** document in state `current`; an integration test proves a
  second insert in that state is rejected by the database, not by application code
- The migration is new and additive — `git log --diff-filter=M` over `marketplace-db-setup/migrations/` shows
  no previously applied migration modified (migrations are immutable)
- All existing DEK-count prose is corrected in the same change: `fieldEncryption.mts:78` and `:105-109` say
  five, and `grep -rn 'four data encryption keys' BEs/ docs/` returns nothing
**Traces:** NFR-SE04, NFR-SE06, NFR-SE07, NFR-SE11, NFR-SE12, NFR-MA01, NFR-MA02, NFR-MA05; ADR-029; BCON-01, BCON-03, BCON-06
**Evidence (gap):** RISK_REGISTER R02; `BEs/marketplace-common/src/encryption/fieldEncryption.mts:78,105-109`
**Outcome — built by E01-S12, by a different store.** The goal is met: more than one key exists at a time and
a key is added without a redeploy. Nothing else in the criteria was met literally, and deliberately. There is
no `signingKey` collection, no migration, no `$jsonSchema` and **no fifth DEK** — the keys are one
AES-256-GCM-wrapped hash at `<REDIS_KEY>keygrip` (`version`, `wrapped`, `fp`), unwrapped with `KEYGRIP_KEK`
and authenticated with the version as AAD (ADR-034 §Record). The "at most one `current`" partial unique index
has no equivalent because the invariant it enforced cannot be violated in the new shape: **there is one
record and one index 0**, so "two current keys" is not a state the store can hold, which is a stronger
guarantee than an index that rejects the second insert. The DEK-count prose was therefore never wrong and
`grep -rn 'four data encryption keys'` was never owed. Redis over Mongo was chosen because every service
already holds a Redis connection on the request path and none of the five signing services opens Mongo for
this — ADR-034 §Options records the comparison.

### E16-S02 — Every service holds a keyring snapshot it refreshes itself   `built`
State plainly: this is the architectural change. A key added to the collection must reach a running process
without restarting it, and it must do so without making cookie signing asynchronous.
**domains:** backend, testing
**Acceptance criteria:**
- `marketplace-common` exports a keyring provider that loads `current` + all `verifiable` keys, holds them in
  memory, and refreshes on a stated interval; `app.keys` is assigned this provider rather than a plain array
- A test asserts the provider exposes `sign`, `verify` and `index` with Keygrip's signatures and that koa's
  cookie layer accepts it — a duck-typed object rather than a `Keygrip` instance. **If koa's `cookies`
  dependency turns out to require a real `Keygrip`, this story instead constructs a fresh `Keygrip` per
  snapshot refresh and the test asserts that.** One of the two must be proven by test, not assumed
- A test asserts `keys[0]` in every snapshot is the `current` key and that the `verifiable` keys follow it —
  Keygrip signs with `keys[0]` and this ordering is the entire correctness argument for rotation
- A snapshot refresh that fails — database unreachable — keeps the previous snapshot and logs, rather than
  emptying the keyring and invalidating every cookie on the platform; tested by making the loader throw
- The refresh interval is a named constant with a test asserting its value, and the resulting **worst-case
  propagation delay** for a rotation is stated in this epic and in `docs/architecture.md`
**Traces:** NFR-SE04, NFR-AV01, NFR-AV02, NFR-MA01, NFR-MA02, NFR-MA05, NFR-PE02; BCON-01, BCON-02, BCON-03
**Evidence (gap):** keys read once at boot in all five cookie-touching services

> The user authorised changing the middleware contract across all five services for this. It turns out not to
> be needed if the provider is duck-typed, because signing stays synchronous against an in-memory snapshot and
> only the *refresh* is async. The authorisation is recorded here so the fallback in the second criterion can
> be taken without re-asking.

**Outcome — built by E01-S13.** `watchKeygrip` in `marketplace-common` is the provider; every criterion is met
in substance and the second one took **its own stated fallback**: no duck-typed object was attempted, a fresh
`Keygrip` is constructed per adoption and `app.keys` is **reassigned** rather than mutated. That choice is
stronger than the criterion asked for and §5 of the E16-S09 finding says why — `cookies` reads `app.keys` per
request, so a request already in flight finishes against the array it started with and no request can observe
a half-swapped keyring. Order is load-bearing and holds: `loadKeygrip` answers newest-first, so index 0 is the
signing key and the rest verify. A failed re-read keeps the previous keys and reports rather than throwing —
`watchKeygrip` catches into `onError`, because killing a serving process over a key it already holds is worse
than serving on with it; the **boot** read is the one where a bad record is fatal. The refresh interval is
`KEYGRIP_POLL_MS = 300_000`, named and asserted. **The worst-case propagation delay is now measured, not
estimated: 37 ms observed to all five services** (E16-S09 §3); the five minutes is the ceiling for a lost
pub/sub nudge. Both figures are in `docs/architecture.md` §Auth model.

### E16-S03 — Rotating mints a new current key and demotes the old one   `built`
**As a** platform operator, **when** I rotate the signing key, **I want** the previous key to keep verifying
existing cookies for a bounded period **so that** nobody is logged out by a rotation.
**domains:** backend, database, testing
**Acceptance criteria:**
- `rotate()` generates a new key with a CSPRNG — `crypto.randomBytes`, never `Math.random()` — inserts it as
  `current`, and demotes the previous `current` to `verifiable`, in an order that never leaves zero documents
  in state `current`; a test asserts the operation order explicitly
- The behaviour when `findCurrent()` returns `null` is specified and tested: rotating an empty keyring inserts
  a first `current` key and demotes nothing, rather than throwing or writing `verifiable: null`
- The generated key's length and encoding are asserted by test against a named constant, and the return value
  of `rotate()` contains **no key material** — a test asserts the returned object's key set exactly
- An integration test rotates, then verifies a cookie signed **before** the rotation still verifies, and a
  cookie signed after it verifies too
**Traces:** NFR-SE01, NFR-SE04, NFR-SE07, NFR-AV01, NFR-MA01, NFR-MA02; BCON-01, BCON-02, BCON-09
**Evidence (gap):** no rotation operation exists
**Outcome — built by E01-S13, as `keygripRotate`.** The demotion criterion is met by construction rather than
by operation order: rotation **prepends** to the list and removes nothing a cookie can still be presented
under — only keys demoted longer ago than `SESSION_CAP_DAYS_REMEMBERED`, counted from the demotion since
the v2.1 fix — so there is no window with zero signing keys because there is never a moment when the list
is rewritten in two steps — the whole record is
replaced under a Lua compare-and-set on `version`, and a losing writer is told so rather than overwriting.
The key is `crypto.randomBytes`, never `Math.random()`, its length and encoding are asserted against a named
constant, and the mutation returns **no key material** — asserted as a substring check over the serialised
response, not a field-shape check. The `findCurrent() === null` branch has no counterpart: a service refuses
to boot without a record, so "rotating an empty keyring" cannot be reached from a running platform; the
empty-store path is `seedKeygripRecord`'s, and its idempotence is E16-S05's. The integration criterion — a
cookie signed before the rotation still verifies after it — is what §5 of the E16-S09 finding proves
structurally and what the rotation's own integration tests cover.

### E16-S04 — Retiring a key is deliberate, guarded, and honest about failure   `built`
**As a** platform operator responding to a suspected key compromise, **when** I retire a key, **I want** it
out of every keyring quickly and **I want** to be told if the retire did not apply **so that** I do not
believe a compromised key is gone when it is not.
**domains:** backend, database, testing
**Acceptance criteria:**
- `forceRetire(keyId)` updates **only** a document whose state is `verifiable` — the filter includes the state,
  so retiring the `current` key is impossible by construction, not by a prior read; a test asserts the exact
  filter
- A `matchedCount === 0` outcome throws a named error rather than returning success, following the precedent
  at `funShopOwnerUpdateStatus.mts:39`; both branches tested
- Retiring the `current` key is refused with its own tested error, and the refusal explains that rotation is
  the operation for that case
- A test asserts a retired key disappears from the next snapshot refresh, and the epic states the resulting
  worst-case window between retiring a key and the last process dropping it
**Traces:** NFR-SE01, NFR-SE04, NFR-SE05, NFR-MA01, NFR-MA02, NFR-CO01; BCON-01, BCON-02
**Evidence (gap):** no retire operation exists
**Outcome — built in this epic's name**, `marketplace-dev-admin-authenticated-resource` commit `c8f5d94`.
`keygripRetire(id)` removes one entry from the record under the same Lua compare-and-set as rotation. The
"filter includes the state" criterion has no literal form — there is no `state` field — and the guarantee it
was buying is met more directly: **the index-0 key is refused by name**, 409 `KEYGRIP_RETIRE_CURRENT`, whose
message says rotation is the operation for that case. The three failure branches are distinct and each is
tested over HTTP: unknown id → 404 `KEYGRIP_RETIRE_UNKNOWN`, current key → 409, lost compare-and-set → 409.
None of them returns success — the `matchedCount === 0` precedent at `funShopOwnerUpdateStatus.mts:39` is
followed in shape if not in API. **The worst-case window between retiring a key and the last process dropping
it is measured, not stated: 8 ms observed to all five services**, ceiling `KEYGRIP_POLL_MS` = 5 minutes if the
nudge is lost (E16-S09 §4). That ceiling is the fail-**open** residual and it is R47.

### E16-S05 — A fresh database bootstraps its own first key   `built`
State plainly: a platform that cannot start without a key, and has no key on a new install, does not start.
**domains:** backend, testing, documentation
**Acceptance criteria:**
- The bootstrap lives under a `lib/` path that the package's Stryker `mutate` glob already covers, is unit
  tested, and reaches Stryker 100 — **or** the epic states an argued exclusion and adds it to the config with
  a comment. A script parked outside the tested tree, silently uncovered, is not acceptable (BCON-02)
- Bootstrapping is idempotent: running it against a database that already has a `current` key changes nothing
  and throws nothing; tested
- `SETUP.md` gains the bootstrap step in its ordered boot sequence, in the same change
- A service starting against a keyless database fails fast with a message naming the bootstrap command, rather
  than serving requests with an empty keyring; tested
**Traces:** NFR-AV01, NFR-AV02, NFR-MA01, NFR-MA02, NFR-MA05, NFR-CO01; BCON-01, BCON-02, BCON-03
**Evidence (gap):** no bootstrap exists — the env var is the current bootstrap
**Outcome — built by E01-S12** as `seedKeygripRecord` in `marketplace-db-setup/lib/keygrip.js`, under the
`lib/` path the criterion required and inside that package's tested tree, so no Stryker exclusion was argued
for. Idempotence is met and is what the criterion asked for: seeding a store that already holds a record
changes nothing and throws nothing, and `--force` is the explicit opt-out. `SETUP.md` carries the step in its
ordered boot sequence. The fail-fast criterion is met by ADR-034's boot gate — a service whose `KEYGRIP_KEK`
cannot unwrap the record, or that finds no record at all, logs and `process.exit(1)`s instead of binding a
port, so it never serves with an empty keyring. **E16-S09 §1 found the one thing wrong with that**, and it is
not this story's: the *message* naming the fix does not reach anyone, because the required-env throw is
swallowed by a DSN-less Sentry and the process exits **0**. That is E18-S03's to fix.

### E16-S07 — The GraphQL surface for key custody returns no key material   `built`
**As a** platform operator, **when** I query the keyring through the Admin API, **I want** metadata and
nothing else **so that** the API cannot become the leak that the env var never was.
**domains:** backend, testing
**Acceptance criteria:**
- `marketplace-dev-admin-authenticated-resource` gains queries and mutations for listing, rotating and
  retiring keys; the GraphQL type for a key has fields for id, state and timestamps and **no** field of any
  kind that could carry key material — asserted by a test that enumerates the type's fields against an exact
  expected set
- A test drives each resolver against a seeded key and asserts the serialised response, as a string, does not
  contain the seeded key's value — a direct substring check, not a field-shape check
- Every resolver is Admin-tier only, going through the existing `assertTier` path with its reject branch
  tested (the same gap E18 closes generally)
- Mutations are rate-limited through `assertUnderRateLimit`, and no bucket key derives from a network address

### E16-S09 — Investigation: what actually happens to a live session across a full rotate-and-retire cycle   `built`
State plainly: the propagation window is arithmetic until someone runs it against five services and watches.
**domains:** backend, testing, documentation
**Acceptance criteria:**
- A written finding records, against the running Dev stack, the observed time from `rotate()` to every one of
  the five cookie-touching services signing with the new key, and from `forceRetire()` to every one of them
  refusing the retired key
- The finding states whether any in-flight refresh can straddle the change badly enough to log a user out, and
  if so, that becomes a story before E16 is called done
- The measured windows replace the estimates in E16-S02, E16-S04 and E16-S08's R42 row
**Traces:** NFR-AV01, NFR-AV02, NFR-MA07; BCON-01, BCON-04
**Evidence (gap):** no rotation has ever been performed on this platform
**Outcome — built 2026-08-13.** The finding is
[`docs/report/keygrip-rotation-propagation.md`](../../../report/keygrip-rotation-propagation.md) v1.0. One
rotation and one retirement were run against the live Dev stack — the first this platform has ever performed
— with all six relevant services up, against an **isolated `e16s09:` Redis namespace under an ephemeral KEK**
so nothing could reach the platform's own keyspace or adopt real key material; the namespace was deleted
afterwards and no `.env` was touched. **Rotation reached all five signers 37 ms after the mutation was
issued, retirement 8 ms**, both bounded above by a 25 ms polling granularity. The holders hash held exactly
five rows, one per cookie-touching service, with the admin resource service correctly absent.

**The straddle question is answered: no story is owed.** A rotation cannot log anyone out at any propagation
delay, and §5 shows this structurally rather than by luck — rotation only ever removes a key that stopped
signing more than a remembered session ago (`isTailRetirable`, corrected 2026-08-28: it reads the demotion
instant, not the key's own age), `cookies` re-signs on a later-index match so sessions migrate themselves, and
`app.keys` is reassigned rather than mutated so an in-flight request finishes against the array it started
with. A retirement does invalidate cookies, which is
its purpose. The one case where it reaches further than intended needs a lagging holder — a **failed** pub/sub
delivery, against 2 ms observed — **and** an operator retiring inside that holder's remaining poll window;
`keygripRetire` already refuses the index-0 key, and the holders table shows the disagreement before the
operator acts. What it earns is a console affordance in **E17-S08** — warn or refuse while a holders row
disagrees — not a domain change: the mutation must not consult the holders hash, because a break-glass
response to a compromised key cannot be blockable by a service that is merely unreachable.

**One defect found, and it is not about keys.** A service failing `checkRequiredEnv()` exits **`0`** with no
output: the throw is outside `start()`'s `try`, and the bottom-of-file `.catch` hands it to
`Sentry.captureException` with no DSN configured. It reads as a clean shutdown. Recorded for **E18-S03**.
The measured windows replace the estimates in E16-S02 and E16-S04 above and in R47.

| 1 | ~~Snapshot refresh interval.~~ **Answered 2026-08-13 by E16-S09, and the question turned out to be the wrong one.** The interval is not the mechanism: adoption rides a `<REDIS_KEY>keygrip:rotated` publish and was measured at **37 ms** to all five services, so `KEYGRIP_POLL_MS = 300_000` is the ceiling for a *lost* message rather than the propagation time. Shortening it would buy nothing on the normal path — already inside one interval end to end — and would cost five reads per service per interval forever. The poll's unchanged branch restamps the holders row, which is what makes 5 minutes also the staleness bound on the heartbeat. **Closed.** | Platform owner |
| 2 | ~~How long does a demoted key stay `verifiable`?~~ **Answered 2026-08-28 — and answering it found the rule implemented against the wrong timestamp.** The figure was never in doubt and is unchanged: `SESSION_CAP_DAYS_REMEMBERED`, **30 days**, decided 2026-08-10 alongside the 1-day default (E14-S05), because this window must cover the longest session anyone can hold rather than the common one. What was wrong is where the thirty days are counted **from**. `rotateKeygripKeys` measured them from the key's own `createdAt`; a key signs until the rotation that *demotes* it, so the last cookie it signed carries a remembered session for thirty days from the **demotion**. On any cadence faster than monthly the two diverge — minted day 0, demoted day 7, cookies alive to day 37, dropped on day 30 — and the customer logged out is one holding a remembered session idle across the window, since an active one re-signs itself on a later-index match. Fixed in `marketplace-common` as `isTailRetirable`, which reads the `createdAt` of the key *in front of* the tail: minting that key is the event that demoted this one, so the instant was in the record all along and `IKeygripKeyMaterial` keeps its three fields ([`ADR-034` §Amendment 2026-08-28](../../phase3/adr/ADR-034-keygrip-keys-live-in-redis-wrapped-under-a-kek.md)). Two corrections come with the answer. **`verifiable` is not a state** — E16-S07's outcome already records that the shipped lifecycle is a position in an ordered array and no `state` field exists, so the question reads as *how long does a key stay in the array after it stops being index 0*. And **the row's own justification was inverted**: it said the 90-day `REFRESH_TOKEN_EXPIRY` is not the bound "since a session past its cap is refused before the key is read", and the order is the other way round — `authenticatedAuthorizationHandler.mts:28` verifies the signature against the whole key array before `resolveAuthorizationSession` ever compares `sessionCapDeadline`. Thirty still beats ninety, for the neighbouring reason: a past-cap session is refused anyway, one line later, so a key kept past the cap protects nobody. The honest window is therefore **at least thirty days after demotion, and in practice until the next rotation after that** — removal is rotation-driven, nothing runs on a timer, and a fleet that stops rotating keeps every key indefinitely at no cost, because a key nobody signs with can only verify cookies that are already alive. **Closed.** | Platform owner |
| 3 | ~~Duck-typed keys object, or a real `Keygrip` rebuilt per snapshot?~~ **Answered by E01-S13: a real `Keygrip`, rebuilt per adoption**, with `app.keys` reassigned rather than mutated. The duck-typed route was not attempted — E16-S02's stated fallback was taken, and it is the better of the two here for a reason the story could not have known: reassignment gives every in-flight request a stable array, which a mutated shared object would not. **Closed.** | Platform dev |
| 4 | ~~Does the CSFLE master key itself have a custody story?~~ **Answered 2026-08-28 by [`ADR-040`](../../phase3/adr/ADR-040-the-secrets-manager-vendor-choice-is-the-adopters.md) — and the answer is *no, and this blueprint will never build one*.** The question survived one retarget already: no CSFLE key encrypts a signing key, because there is no encrypted collection — the wrapping key is `KEYGRIP_KEK`, a per-machine `env` value, and this row has asked about **that** since R02 closed on 2026-08-13 (E18-S07) by splitting its residual out into **R50** rather than solving it. `ADR-034` named a secrets manager as the destination and blocked it on `ADR-032`; `ADR-039` unblocked it on 2026-08-28; asked to choose, the platform owner ruled that *"a blueprint cannot make the vendor decision — Vault vs SOPS vs AWS KMS vs GCP depends on where the adopter deploys"*, which delegates the custody story permanently to whoever deploys this — the line `ADR-037` draws for hosting and `ADR-038` for commerce. ⚠️ **What closes here is the design question this row asks, not the operational one R50 names.** `R50` is `Accepted (see §5)` the same date with its score and residual unchanged: still a hand copy onto six services and the seed, still no escrow, still nothing checking the value before a deploy, and the boot-time `KEYGRIP_KEK_MISMATCH` gate still the only check. The swap points an adopter needs are in [`docs/PRODUCTION_HARDENING.md`](../../../PRODUCTION_HARDENING.md) §1. **Closed.** | Platform owner (ADR-034, ADR-040) |
