## 1. Epic goal

Make a refresh token single-use and make a session mortal. Today rotation mints a new pair and deletes the
old refresh key, but a copy of that old token stolen before rotation is indistinguishable from an expired
one, the old access token keeps working for up to 91 more minutes, and a session that is touched once a
quarter never ends. This epic gives every session lineage an identity (a *family*), tombstones a consumed
refresh token so a replay is *detected* rather than merely refused, caps every session at an absolute age
regardless of activity — one day by default, thirty when the user asks to be remembered — and in doing so
finally makes `rememberMe` mean something.

## 4. Stories

### E14-S01 — A refresh session carries the identity of its lineage   `built`
State plainly: the refresh hash must carry a `familyId` (constant for the whole rotation chain born of one
login), an `originalLogin` epoch-millis stamp, and the `sessionCapDays` resolved at login — and a session
missing any of them must be rejected structurally, not defaulted.
**domains:** backend, testing
**Acceptance criteria:**
- `IRefreshData` declares `familyId: string`, `originalLogin: string`, `sessionCapDays: string` as required,
  non-optional fields — `BEs/marketplace-common/src/others/IRefreshData.mts`
- `resolveAuthorizationSession` rejects a refresh hash whose `familyId`, `originalLogin` or `sessionCapDays`
  is absent, by the same fail-closed shape `assertTier` already uses for a missing `tier`
  (`BEs/marketplace-common/src/others/assertTier.mts:13-16`), with one unit test per missing field asserting
  `rejects.toThrow` and **not** a wildcard accept
- The four login writers (`setRedisLoginSession.mts` and its `Admin`/`ShopOwner`/`User` siblings in
  `BEs/dev/marketplace-dev-public-authorization/src/lib/db/redis/`) each `hSet` all three fields; one unit
  test per writer asserts the exact hash shape with `toStrictEqual`, not a subset match
- `yarn test:cov` 100% on all four metrics and `yarn test:mutation` Stryker 100 in `marketplace-common` and
  in `marketplace-dev-public-authorization`, no threshold touched (BCON-02)
**Traces:** NFR-SE01, NFR-SE05, NFR-MA01, NFR-MA02, NFR-MA05; ADR-003, ADR-004; BCON-01, BCON-02
**Evidence (gap):** `BEs/marketplace-common/src/others/IRefreshData.mts:11-14`

> **Why the fields are required rather than optional.** A pre-existing session minted before this lands has
> `familyId === undefined`. If the field were optional, the first rotation after deploy would write every
> such session into one shared `family:undefined` set, and a single reuse event would then mass-revoke
> unrelated accounts. Rejecting structurally converts that into a one-time forced re-login for sessions
> older than the deploy — loud, bounded, and correct — instead of a silent cross-account blast radius.

### E14-S02 — A consumed refresh token is tombstoned before it is deleted   `built`
State plainly: rotation must leave a durable, non-replayable marker that a specific refresh token was
consumed, and that marker must exist *before* the token's own key is removed.
**domains:** backend, testing
**Acceptance criteria:**
- `refreshSessionTokens` writes `${REDIS_KEY}used:${sha256(oldRefreshToken)}` holding `{ familyId }` with TTL
  `REFRESH_TOKEN_EXPIRY`, and this write is ordered strictly **before** the existing
  `del(old refresh key)` at `refreshSessionTokens.mts:100`
- The unit test asserts the full call order with `toHaveBeenCalledExactlyOnceWith` per step — `hSet` new pair
  → `expire` new pair → family `sAdd` → tombstone `hSet`+`expire` → `setLoginCookies` → `del` old access →
  `del` old refresh — so a reordering is a caught Stryker mutant, not a passing rewrite
- The tombstone key is a SHA-256 hex digest, never the token itself; a unit test asserts the key argument
  matches `/^[0-9a-f]{64}$/` after the `REDIS_KEY`+`used:` prefix
- Every Redis command added here is single-key (BCON-08) — no `del` takes more than one argument anywhere in
  the diff, asserted by the same call-order test
- `ISessionWriteStore` gains `sAdd`, taking its docstring from "the three Redis commands the rotation issues"
  to four; E14-S08 takes it to six, and whichever lands last owns the final sentence. The `family:` key it
  writes is `expire`d to `REFRESH_TOKEN_EXPIRY`, the physical TTL, so the set outlives every member it names
  and no live session is left unrevocable
**Traces:** NFR-SE01, NFR-SE03, NFR-SC03, NFR-MA01, NFR-MA02; ADR-003; BCON-01, BCON-08
**Evidence (gap):** `BEs/marketplace-common/src/others/refreshSessionTokens.mts:100`

> **Ordering is the whole control.** Delete-then-tombstone leaves a window in which a process death produces
> a consumed token with no marker; a later replay of it then looks exactly like ordinary expiry, silently
> reopening §3.1. Tombstone-then-delete makes that window structurally impossible: the old key never becomes
> unresolvable without its marker already in place. Until the delete lands, the old key still resolves
> normally, so a tombstone written early is invisible — `resolveAuthorizationSession` checks the live key
> first and consults the tombstone only on a miss.

### E14-S03 — Replaying a consumed refresh token kills the whole family   `built`
**As a** platform operator, **when** a refresh token that was already consumed is presented again outside the
grace window, **I want** every access and refresh key descended from the same login destroyed **so that** a
stolen token is worth at most one rotation instead of an indefinite parallel session.
**domains:** backend, testing
**Acceptance criteria:**
- On a live-key miss, `resolveAuthorizationSession` reads `${REDIS_KEY}used:${sha256(token)}`; a hit past the
  grace window calls the family-revocation routine and then throws, and a unit test asserts *both* — the
  revocation calls and the `rejects.toThrow` — not the throw alone
- Revocation lives in its own `marketplace-common` module as `revokeSessionFamily({ store, familyId })`,
  exported from `package.json`, taking its own two-method `ISessionFamilyStore { sMembers, del }`.
  `ISessionReadStore` is declared as `extends ISessionFamilyStore`, adding `hGetAll` — so the resolver hands
  its own `store` straight to the routine, one parameter and one injection point, unchanged at all three call
  sites
- Revocation reads `${REDIS_KEY}family:<familyId>` with `sMembers`, issues **one single-key `del` per member**
  (BCON-08), and deletes the family key last; the unit test asserts one `del` call per member with exact
  arguments and asserts `del` is never invoked with two keys, against a stub carrying those two methods and
  no `hGetAll`
- `resolveAuthorizationSession`'s docstring stops claiming "the single Redis command this resolver issues"
  and states what is now true: one command on the resolving path, and on a replay hit a delegation to
  `revokeSessionFamily` costing 1 + N. A stale docstring here is worse than none — it is the sentence the
  next reader will size the auth path by
- A family whose members have already expired revokes without throwing — the miss is a Redis no-op, proven by
  a unit test seeding a member key that does not exist
- `marketplace-common` `yarn test:cov` 100/4 and `yarn test:mutation` 100 including both boundary mutants on
  the grace comparison (at the boundary and boundary ±1), per the repo's weak-assertion table
**Traces:** NFR-SE01, NFR-SE03, NFR-SE05, NFR-SC03, NFR-MA01, NFR-MA02; ADR-003, ADR-005; BCON-01, BCON-08
**Evidence (gap):** `BEs/marketplace-common/src/others/resolveAuthorizationSession.mts:70-71`

> **Decided 2026-08-10: the interface widens, the routine moves out.** The alternative on the table was a
> second store parameter so `ISessionReadStore` could keep its one method. It was rejected because there is
> exactly one implementation and it is the same `redisClient`: a second parameter means passing that object
> twice at all three call sites, buying a segregation nothing consumes.
>
> **The objection it was raised against is still answered, by extraction rather than by parameter count.**
> `revokeSessionFamily` is independently testable against a stub with no `hGetAll` on it, and the resolver's
> own tests go on testing resolution. That also matches E15-S04, which already commits to a standalone
> `revokeAllSessionsForAccount` in `marketplace-common` doing the identical one-`del`-per-member walk over a
> different structure — so this is consistency with a decision E15 already made, not an E14 judgement call.
>
> **On the N-delete loop being on a per-request auth path: it is not.** `hGetAll` stays the only command a
> resolving request issues. The 1 + N walk runs on a replay hit, which E14-S02's tombstone makes a
> once-per-family event. The cost lands on the request that discovered a theft, which is the right request
> to spend it on.

### E14-S04 — A concurrent refresh inside the grace window is benign, and stores no token   `built`
**As a** customer with several tabs open, **when** two tabs fire `refresh` at the same moment and one loses
the race, **I want** the loser told to retry rather than logged out or silently double-rotated **so that**
ordinary multi-tab use is not mistaken for token theft.
**domains:** backend, frontend, testing
**Acceptance criteria:**
- `marketplace-common` exports `GRACE_SECONDS = 10`, decided 2026-08-10, with a unit test asserting the exact
  value — a single constant, not a per-tier or per-SPA value, since the race it covers is a network round trip
  and does not vary by who is logged in
- A tombstone hit **within** `GRACE_SECONDS` of `consumedAt` throws a distinct, named retryable error and
  does **not** revoke the family; a tombstone hit past it revokes (E14-S03). Both branches have their own
  unit test and both sides of the boundary comparison are covered
- Every grace hit increments a counter — a count and nothing else, no token, no key, no account id. A window
  that is never hit is a window that can be shortened, and one hit constantly means an SPA is refreshing in a
  loop; neither is visible without the count
- The tombstone value contains `familyId` and `consumedAt` **only**. A unit test asserts
  `Object.keys(value)` equals exactly that two-element set — no successor access token, no successor refresh
  token, no prefix of either, ever written as a Redis value
- All three frontends retry a `refresh` that answers the retryable error at most twice before surfacing a
  logout, with a component test per SPA driving the error path — `marketplace-admin`,
  `marketplace-shopowner`, `marketplace-user`
- Each SPA's own `yarn test` coverage thresholds are met with the new branch included; no threshold lowered
**Traces:** NFR-SE01, NFR-SE02, NFR-MA01, NFR-MA02, NFR-CO01; ADR-003, ADR-018; BCON-01, BCON-02
**Evidence (gap):** no grace concept exists — `BEs/marketplace-common/src/others/resolveAuthorizationSession.mts:63-71`

> **Why ten seconds.** The race this window covers is bounded by one request round trip, not by how long a
> tab sits idle. The refresh token is a root-scoped `HttpOnly` cookie, so every tab shares one cookie jar and
> a tab that wakes up an hour later sends whatever cookie is current rather than a stale copy of its own. The
> only way to present a consumed token is to have dispatched before the winner's `Set-Cookie` was written —
> so the spread is the winning request's round trip plus the browser's cookie write, which is milliseconds on
> a desktop and low single-digit seconds on a poor mobile connection. Ten covers that several times over.
>
> **What each direction costs, since they are not symmetric.** Too narrow and ordinary multi-tab use revokes
> the whole family: a legitimate user is logged out of every session they have, loudly and wrongly. Too wide
> and an attacker replaying a stolen refresh token inside the window is told to retry instead of tripping the
> revocation — note that they gain **no tokens** either way, since the grace branch mints nothing (see the
> rejected alternative below); what a wide window costs is *detection*, not access. A false positive is
> therefore worse than a false negative here, which is why the number is not 1 or 2.
>
> **E14-S09 can lower this, not raise it.** The measurement it produces is of real client behaviour; if the
> observed spread is under a second, 10 stays as headroom or drops with the data behind it. Raising it needs a
> reason written down, because past about a minute the tombstone stops functioning as reuse detection at all.
>
> **Measured, 2026-08-10 — 10 confirmed.** Eighteen simultaneous two-tab reloads against the running Dev
> stack: spread 0.6 ms median, 49.9 ms worst, nothing near ten seconds. It was **not** lowered anyway, and the
> reason is that the measurement is of *dispatch* spread on loopback while the quantity the window must cover
> is that spread plus the loser's own request latency — the term a sub-millisecond transport cannot show. The
> asymmetry two paragraphs up decides the rest: narrowing on evidence that omits the justifying term costs a
> legitimate user their whole family. See [`multi-tab-refresh-behaviour.md`](../../../report/multi-tab-refresh-behaviour.md) §6.

> **Rejected alternative, recorded so it is not re-proposed.** The first design cached the successor pair at
> `${REDIS_KEY}grace:${sha256(token)}` and replayed it to the loser. It was dropped for two independent
> reasons. First, it would store a live, directly replayable credential as a Redis **value**, which directly
> contradicts E13's stated outcome that a post-migration RDB/AOF dump yields no string usable as a Bearer
> token. Second, it had no implementable path: `resolveAuthorizationSession` runs inside the koa middleware
> (`authenticatedAuthorizationHandler.mts:26-51`), takes no `ctx`, and returns `TAuthorizationSession | null`
> — it cannot call `setLoginCookies`, and `refresh.mts:19-25` calls `refreshSessionTokens` unconditionally,
> so a "grace hit" would have minted a third pair anyway. The retry outcome needs neither: the middleware
> throws, the resolver never runs, and by the time the client retries its cookie jar already holds the
> winner's cookie.

### E14-S05 — A session dies of old age no matter how often it is used   `built`
**As a** platform operator, **when** a session has existed longer than the absolute cap, **I want** it refused
on the next refresh regardless of activity **so that** a token stolen from a long-lived session has a bounded
useful life.
**domains:** backend, testing
**Acceptance criteria:**
- A new `marketplace-common` export declares **two** constants — `SESSION_CAP_DAYS_DEFAULT = 1` and
  `SESSION_CAP_DAYS_REMEMBERED = 30` — and a unit test asserts each exact value. The two differ, both are
  reachable from E14-S07's two branches, and a mutant that swaps or alters either is killed by the branch test
  that reads it, so no suppression is needed anywhere
- **Neither is a `Tier`-keyed map.** An earlier draft proposed one, and a map whose three entries hold the same
  number cannot be tested: a mutant that reads the wrong tier's entry returns the same value, so no test that
  could exist kills it, and mutation score 100 becomes reachable only through a `Stryker disable` this
  workspace does not allow. The distinction this platform actually makes is `rememberMe`, not tier, and the
  constants say exactly that. If the tiers ever diverge, the map arrives with the story that makes them diverge
- `resolveAuthorizationSession`, after `assertTier` and before returning, refuses a session where
  `now - originalLogin > sessionCapDays * 86400_000`, throwing the **same** existing
  `throwRefreshTokenExpiredOrDeleted()` — no new error class, no new taxonomy — and runs the same
  family-revocation routine as E14-S03
- Boundary tests exist at exactly the cap, one millisecond under, and one millisecond over, so the comparison
  survives Stryker's relational-operator mutants
- `REFRESH_TOKEN_EXPIRY` is not edited anywhere; `grep -rn 'REFRESH_TOKEN_EXPIRY' BEs/` shows it still read
  from `@axiumine/koa-utils`, never redefined
**Traces:** NFR-SE01, NFR-SE03, NFR-MA01, NFR-MA02, NFR-MA05; ADR-003; BCON-01, BCON-02
**Evidence (gap):** `node_modules/@axiumine/koa-utils/dist/lib/tokens.mjs` (90-day sliding TTL, no ceiling)

> **Decided 2026-08-10: one day by default, thirty when remembered.** The draft proposed a privilege gradient
> — Admin 7, ShopOwner 30, User 90 — then a single uniform seven. Both were rejected in favour of splitting on
> the control the user actually operates: the cap follows the checkbox, not the tier. An unchecked login is a
> shared-device login and dies overnight; a checked one is the thirty days the login form has always implied
> and never delivered. Thirty is therefore not an estimate — it is the promise the UI was already making, now
> enforced server-side for the first time.
>
> **Why the split is safe to test, unlike the uniform number.** One and thirty are distinct values reached by
> the two halves of one branch, so every mutant that touches either constant dies on a test that has to exist
> anyway. The uniform seven had the opposite property in map form, which is what killed the map.
>
> **What it costs, recorded so a later reversal is a decision rather than a discovery.** A remembered session
> now survives thirty days of pure inactivity, which is thirty days of useful life for a stolen refresh token
> whose theft is never noticed — the widest exposure this epic leaves open, and the reason E14-S02's
> reuse-detection and E14-S03's family revocation carry more weight under this decision than under the
> rejected seven. Against that: the default is now one day rather than seven, so the common case of a customer
> who does not tick the box is six times tighter than the rejected model, and a shared device forgets by
> morning. Reversing either number is one constant plus its test; the structure does not have to change.
>
> **What it does not change.** `REFRESH_TOKEN_EXPIRY` stays at 90 days — the physical Redis TTL is untouched
> by this story and remains the safety net under both caps, never the binding limit, since 30 < 90. E13's
> 90-day dual-read window is anchored to that TTL and not to either of these numbers, so it does not move: a
> raw-shape key can still physically exist for 90 days whatever the cap refuses.

### E14-S07 — `rememberMe` chooses the server-side cap   `built`
**As a** customer on a shared device, **when** I leave "remember me" unchecked, **I want** my session to die

### E14-S08 — `refresh` is rate-limited without capturing a client IP   `built`
State plainly: the `refresh` endpoint must cost an attacker something per attempt, and no control introduced
for that purpose may capture, hash, truncate or store a client IP address.
**domains:** backend, testing
**Acceptance criteria:**
- A **pre-lookup** limiter runs inside each authorization service's middleware, before the `hGetAll` at
  `resolveAuthorizationSession.mts:70`, keyed on `hashSessionToken(presented refresh token)` — E13-S01's
  helper, not a second hashing call site — in a `refresh:` bucket, at **20 attempts per 60 seconds**. It is
  the only identity available at that point in the call stack, and it is the tighter of the two limits by
  design: for a live token both buckets increment and the smaller binds, so this one has to be the one that
  binds. Its unique job is metering tokens that never resolve to a family at all — garbage, expired,
  tombstoned — where the family bucket is never reached. It stays in service middleware using `redisClient`
  directly, exactly as `guardPublicLogin.mts:46` does, so it adds nothing to `ISessionReadStore` — that
  interface's only growth is E14-S03's two family methods
- A **post-lookup** limiter keyed on `familyId` runs at **20 per 3600 seconds** — the platform's existing
  `RATE_WINDOW_SECONDS` — and is incremented **only on the path that actually mints a new token pair**. Not
  on grace-served requests, not on rejected ones. A request that mints nothing must not count, or an
  eight-tab wake-from-sleep burst spends sixteen of the allowance in one second and the limit has to be
  loosened until it means nothing
- Both use the existing `assertUnderRateLimit` unchanged, including its deliberate arm-once TTL behaviour at
  `assertUnderRateLimit.mts:52-56` — the expiry is **not** pushed forward on every call
- `ISessionWriteStore` gains `incr` and `ttl`, which is what makes it satisfy `IRateLimitStore` structurally.
  No new interface and no new injection point — a unit test passes one stub for both roles. Its docstring
  says "the three Redis commands the rotation issues" and by the end of this epic the count is **six**:
  `hSet`, `expire`, `del` today, plus `sAdd` from E14-S02's family write and these two. Whichever story lands
  last owns correcting that sentence, and E14-S02 and this one each state the number they leave behind
- `grep -rniE '(remote_addr|x-forwarded-for|\bip\b)' ` over the whole diff of this story returns zero hits;
  no rate-limit bucket, log line, Redis key or Sentry field derives from a network address
- Per-service `yarn test:cov` 100/4 and `yarn test:mutation` 100 including the 429 path

**Evidence (gap):** zero `assertUnderRateLimit` call sites in any `refresh.mts` or authorization middleware

> **Decided 2026-08-10: two windows, not one.** The draft proposed 10 attempts / 60 seconds for the family
> and left the pre-lookup window unstated. Both halves changed, because the two buckets meter phenomena on
> different timescales and giving them one window makes one of them useless.
>
> **Why the pre-lookup window is short.** This is the only Redis structure an attacker can create at will,
> one key per distinct garbage token, and it is the same vector the residual below admits is not closable
> here. Each key costs `rl:refresh:` plus 64 hex characters. At a thousand distinct tokens a second a
> 60-second window holds roughly 60k keys — around 10 MB steady state — where the platform's usual 3600
> would hold 3.6M, around 600 MB. A factor of sixty, on precisely the vector with no other bound.
>
> **Why the family window is long, and 60 seconds would have been the wrong number.** A 60-second window
> resets sixty times an hour, so a steady five rotations a minute never trips it: the pattern only an
> hour-long window can see is exactly the one this bucket exists for. Family keys are bounded by real
> sessions rather than by attacker input, so the long window costs nothing in memory.
>
> **Why 20 an hour is generous rather than tight.** Counting mints instead of requests is what makes it so.
> All tabs share one root-scoped cookie, so one winner rotates for all of them however many are open; a
> legitimate lineage mints once or twice an hour whatever the tab count. Ten times headroom, and still low
> enough to end a rotation loop.
>
> **What this bucket does not buy, recorded so it is not over-trusted.** A replayed tombstoned token triggers
> E14-S03's family revocation on the first hit, so the family limiter never sees sustained replay — the
> detection path gets there first. Its value is bounding write load and rotation churn, not stopping an
> attacker who already holds a valid token. The pre-lookup limiter is the one carrying weight here.
>
> **Named residual, accepted 2026-08-10 as topology-blocked.** `login` carries an IP-keyed bucket today;
> `refresh` deliberately will not, under the standing GDPR decision. Flooding the endpoint with *distinct*
> garbage tokens therefore gets a fresh pre-lookup bucket each time and nothing inside Node can key on the
> one identity that would bound it. Not closable in code from inside this workspace, and this epic does not
> pretend otherwise.
>
> **The edge control it hands off to is written, not missing — which is a weaker residual than an earlier
> draft of this note claimed.** All three rotation endpoints already carry a per-address `limit_req`:
> `/user-authenticated-authorization` on the apex, `/authenticated-authorization` on the shop-owner host and
> `/admin-authenticated-authorization` on the admin host. What is unbuilt is the host nginx runs on, not the
> rule. No new ADR is owed for the control itself; the production-topology ADR `ADR-INDEX.md` §5 already
> records as owed absorbs it, and writing a second would duplicate config that exists and is tested.
>
> **Two E12 dependencies decide whether that hand-off is real.** Both are named here because a residual
> accepted against a control that does not work is not an accepted residual.
> - **E12-S09.** Behind Cloudflare's orange cloud every zone keys on an edge address, so all visitors share
>   one bucket and the flood becomes a platform-wide 429 rather than a bounded one. `set_real_ip_from` plus
>   `real_ip_header CF-Connecting-IP` is what makes per-address limiting mean anything here.
> - **E12-S09's new zone split, which this story is the reason for.** Each vhost's rotation endpoint shares
>   its zone with that vhost's login endpoint, so this flood spends the login allowance for every visitor
>   behind the same address — turning a Redis-cost nuisance into a login-denial vector. Rotation moves to
>   `mkt_refresh` / `mkt_owner_refresh` / `mkt_admin_refresh`.
>
> **What the GDPR position actually is here, written down rather than inferred.** After E12-S09 the edge
> holds a binary client address in `limit_req_zone` shared memory for the zone's lifetime. RAM only: E12-S07
> keeps it out of `log_format`, E12-S10 removes the per-address Redis bucket, and no Node service ever
> receives it. That is the accepted shape. The alternative that keeps the address out of vendor-operated
> infrastructure entirely is Cloudflare's own rate-limiting rules, which costs plan tier rather than code —
> it is not chosen here, and it stays available without invalidating anything above.

### E14-S09 — Investigation: how the three SPAs actually behave with several tabs open   `built`
State plainly: the grace window's length is a guess until someone observes what the real clients do when two
tabs refresh at once — this story produces that observation and nothing else.
**domains:** frontend, testing, documentation
**Acceptance criteria:**
- A written finding records, per SPA, whether concurrent `refresh` calls are possible at all (urql exchange
  behaviour, any existing in-flight de-duplication) and the measured spread between two tabs' refresh calls,
  captured against the running Dev stack
- The finding **confirms `GRACE_SECONDS = 10` or lowers it**, with the measured spread behind whichever it
  says. It may not raise it without a written reason: past roughly a minute the tombstone stops working as
  reuse detection. If the measured spread exceeds 10 seconds the finding says so explicitly rather than
  quietly proposing a larger number, because that result means something other than a race — a retry loop, or
  an SPA holding its own copy of the token outside the cookie jar
- If any SPA already de-duplicates in-flight refreshes, the finding says so explicitly — that would make
  E14-S04's retry path unreachable for that SPA and it must not be written as dead code carrying a test
**Traces:** NFR-MA07; BCON-01, BCON-04
**Evidence (gap):** audit §5 — "Multi-tab concurrent-refresh behaviour was not examined."
**Finding:** [`docs/report/multi-tab-refresh-behaviour.md`](../../../report/multi-tab-refresh-behaviour.md)
v1.0, measured against the running Dev stack (ShopOwner tier end to end, Admin and User by identical
wiring). All three criteria answered: every SPA already de-duplicates in-flight refreshes so a race is only
possible *across tabs*; the measured spread is 0.6 ms median and 49.9 ms worst over eighteen simultaneous
double reloads, explicitly **not** above 10 s; `GRACE_SECONDS = 10` is **confirmed, not lowered**, because
the window must cover the spread *plus the loser's own request latency* and loopback cannot measure the
second term. The investigation also found two defects that are not in this epic's design — a sub-5.6 ms
window in which two refreshes on one token both succeed and fork the lineage, and a 409 whose served body
carries no `extensions.code`, which makes E14-S04's retry path unreachable in all three SPAs. Both are §9 of
the finding, neither is closed here.
