## 1. Epic goal

Give the operator the two things they did not have over a customer account: **a list of them, and a
switch.** `marketplace-admin` had a shop-owners table, a categories screen and a session console, no
customers screen at all, and the Admin resource service had no `user*` operation of any kind. It now has
`usersActiveTbl` and `userUpdateStatus`, and the console has a sixth section at `/customers`.

⚠️ **The lever was a hole, not a feature request.** `user.disabled` already existed in the validator
(`account.js` `DISABLED`) and was already enforced everywhere it matters — `tryLoginUser` refuses the
login, `tokenInfoUser` refuses the session, `funUserUpdatePwd` refuses the password change. What was
missing was the only thing that could ever set it, so suspending a customer meant a write made by hand
against MongoDB — a production write nobody reviews, on the one collection encrypted whole. E19-S03 is
that write, and it does one thing the hand-made update never did: it ends the sessions the customer is
already holding, so the suspension bites now rather than at the next rotation.

⚠️ **The list is bounded by ADR-029, and stayed inside it.** `user` was the collection with no operator
table, and `lib/schemas/user.js` said so in as many words — every personal field is encrypted precisely
*because* nothing sorts, searches or paginates customers. This epic did not reverse that: the table sorts
and filters on fields that were never encrypted, and the encrypted ones are displayed or not displayed,
never queried. No field changed algorithm and no database was rebuilt. See E19-S05, the anti-story that
keeps it that way, and the amended comment in `lib/schemas/user.js`, which now says the narrower thing:
there is an operator table, and it reads nothing encrypted.

## 4. Stories

Landing order is the story order: the index before the query that needs it, the query before the screen
that renders it, the anti-story alongside all three, the documentation last.

### E19-S01 — One compound index on `user`, in a new migration   `built 2026-08-25`
Technical story. Give `usersActiveTbl` an index to sort and page on, so the operator's first screen is not
a collection scan that grows with every signup.
**domains:** database, migrations
**Acceptance criteria:**
- A **new** migration file under `BEs/marketplace-db-setup/migrations/` creates
  `{deleted: 1, disabled: 1, registeredAt: -1, _id: -1}` on `user`, named `tbl_active_registeredAt` to
  match its `shopOwner` counterpart. `20260301000300-create-user.js` is not edited.
- ESR order, with `_id` as the tiebreak, for the same reason `phase4/ERD.md:360` gives on `shopOwner`:
  equality fields first, then the sort, then a unique tail so a page boundary cannot repeat or skip a row.
- Its `down` drops that index and nothing else.
- No field on `user` changes shape, type or encryption algorithm, so no database is rebuilt
  ([`CLAUDE.md`](../../../../CLAUDE.md) — a `lib/schemas/` change would have meant rebuilding every
  database that has run these migrations; this is not one).
**Traces:** `phase4/ERD.md` §Indexes; ADR-014 (migrations).

**Outcome — built.** `BEs/marketplace-db-setup/migrations/20260825000000-user-add-tbl-active-index.js`: `up`
creates `tbl_active_registeredAt` `{deleted:1,disabled:1,registeredAt:-1,_id:-1}` on `user`, `down` drops that
index and nothing else, and `20260301000300-create-user.js` was not opened. `test/migrations.test.mjs` pins the
collection's index set to exactly `['login.email_unique','tbl_active_registeredAt']` and the key order with it,
so a future migration that adds a second one has to say so in a test. No `lib/schemas/` file changed, so no
database was rebuilt.

### E19-S02 — `usersActiveTbl` on the Admin resource service   `built 2026-08-25`
As an operator, I want a paginated list of registered customers, so that I can find the account a support
request is about without opening a database shell.
**domains:** backend, GraphQL, Admin tier
**Acceptance criteria:**
- New query in `marketplace-dev-admin-authenticated-resource` (port 4024 — a domain read, so the
  **resource** service, never the authorization one).
- Arguments mirror `shopOwnersActiveTbl` **minus `search`**: `offset: Int! = 0`,
  `limit: Int! = USERS_TBL_DEFAULT_LIMIT`, `sortDir: SortDirection! = DESC`, and filters for `disabled`,
  `deleted` and `emailVerify.valid`.
- `sortBy: UsersTblSortField! = REGISTERED_AT`, and the enum has **exactly one member**. It is an enum
  rather than a dropped argument so the client shape matches the shop-owner table and a second sortable
  clear field can be added without a breaking change — not because a second one is planned.
- The row carries `_id`, `login.email`, `registeredAt`, `disabled`, `deleted` and `emailVerify.valid`, and
  nothing from `personalData` or `addresses[]`.
- ⚠️ **`login.email` is returned but never ordered or matched by prefix.** It is deterministic, so the
  driver decrypts it on the way out and an *equality* lookup on it works — that is what makes "find the
  account for this address" possible. Deterministic ciphertext preserves equality and nothing else
  (ADR-029), so it sorts in ciphertext order, which is not alphabetical order and is not the operator's
  order either.
- The page total is counted under the same filter as the rows.
**Traces:** `phase4/API_CONTRACTS.md` §Admin resource — queries; ADR-029; ADR-002 (Admin tier = the
`admin` collection it authenticated against, not a role check).

**Outcome — built.** `src/graphQLApi/schema/queries/usersActiveTbl.mts` is the wire contract and a
pass-through; `src/lib/user/usersActiveTblDb.mts` holds the paging, the filter and the count, which runs under
the same filter as the rows. Three types came with it — `GraphQLUserActiveTbl`, `GraphQLUsersActiveTblPage`,
`GraphQLUsersTblSort` — and `UsersTblSortField` has the single member the story asked for. One shape decision
was made in the writing rather than in the plan: `disabled` and `deleted` are `Boolean!` **with server-side
defaults** while `emailVerified` is nullable, because the first two are the index's leading keys and a nullable
"either" state there unbinds them and turns the sort into a blocking one. `emailVerified` sits outside the
index and filters what the index already bounded, so it can afford to be optional. No `search` argument exists
and both files say where it would have gone and why it is not there.

### E19-S03 — `userUpdateStatus`, the missing writer   `built 2026-08-25`
As an operator, I want to disable and re-enable a customer account, so that a compromised or abusive
account can be stopped without a hand-written database update.
**domains:** backend, GraphQL, Admin tier, sessions
**Acceptance criteria:**
- New mutation in the same service: `_id: ID!`, `disabled: Boolean!`, answering `Boolean!` like the other
  twenty-one on this tier.
- **`disabled` is the only argument and it is `Boolean!`**, for the reason `shopOwnerUpdateStatus`
  documents: a nullable flag makes the mutation a partial update, and `null` for "leave alone" and `null`
  for "clear it" are the same wire value, so turning a flag *off* becomes inexpressible. There is no
  `waitApprov` counterpart and there will not be one.
- After the Mongo write lands — never before it — every session that customer holds is revoked, via a
  `endEveryUserSession` built the way `endEveryShopOwnerSession` is: `revokeAllSessionsForAccount` with
  `TIER.user`. ⚠️ **The tier constant is not incidental** — the session index is per tier, so
  `TIER.shopOwner` with a customer's `_id` reads an index that does not exist, deletes nothing, and
  reports success.
- Re-enabling revokes nothing: nobody's credentials changed, and logging a customer out as a *reward* for
  being re-enabled is not a control (E15-S07's rule, and the same reading `shopOwnerUpdateStatus` gives).
- The operator's own session is untouched — this is the cross-account revoke, not E15-S05's "the caller
  goes too", which is a rule about whose credentials changed.
- ⚠️ **There is no residual, and this criterion said there was one.** Written as "one access-token lifetime,
  as it is for `shopOwner`" — false since R54 (2026-08-13): `revokeAllSessionsForAccount` retires **both
  halves of every session**, reading each `accessKey` out of the session hash before deleting the hash, so
  the access token dies with the refresh one. The suspension is immediate and the mutation's docblock says
  so. No access-token deny list is needed and none is built. The comment on `endEveryShopOwnerSession` still
  carries the old claim; correcting it is E15's file, not this epic's.
**Traces:** E15-S06/E15-S07 (cross-account revoke); `phase5/SEQUENCE_DIAGRAMS.md` §2.8 (the shop-owner
shape this mirrors); ADR-002.

**Outcome — built.** `schema/mutations/userUpdateStatus.mts` → `src/lib/user/funUserUpdateStatus.mts` for the
write, then `src/lib/auth/endEveryUserSession.mts` — `revokeAllSessionsForAccount` with `TIER.user`, after the
Mongo write and only when `disabled` is true. The argument is the **target state, not a transition**: the
operator app sends the toggle's state on every save, so re-disabling an already-disabled customer revokes again,
which costs one `hKeys` over an already-empty index and is cheaper than the read-then-write window the
alternative opens. Re-enabling revokes nothing, deliberately. The one criterion above that was wrong when
written — the access-token residual — is corrected in place rather than quietly dropped.

### E19-S04 — the `/customers` screen in `marketplace-admin`   `built 2026-08-25`
As an operator, I want the customers list and its enable/disable switch in the console I already use, so
that suspending an account is one click behind the same login as everything else.
**domains:** frontend, Admin SPA
**Acceptance criteria:**
- A feature directory `src/features/customers/` and a page under `src/pages/`, mirroring
  `TblShopOwners.tsx` / `ShopOwnersPage.tsx` in layout and in its pagination controls.
- Columns: email, registered date (`en-GB`, like every other date on this platform), and the status the
  three flags add up to. **No name column, no city column, no address column** — see E19-S05.
- The status control writes through `userUpdateStatus` and shows the row as disabled immediately after,
  including the fact that the customer's sessions have just ended.
- The screen has no free-text search box, and no sort control on any column but the registered date. An
  input that silently matches nothing is worse than an absent one.
- Nav entry alongside the shop-owners one; it is the operator's fourth surface, not a sub-page of a
  shop owner.
**Traces:** [`docs/frontends.md`](../../../frontends.md); E19-S02, E19-S03 (cannot precede either).

**Outcome — built.** `src/features/customers/TblCustomers.tsx` and `src/pages/CustomersPage.tsx`, on
`/customers`, with a sixth `SideMenu` entry. Two things the story did not anticipate: the screen needs an
explicit **active / suspended filter**, because `usersActiveTbl` takes required `disabled` and `deleted`
booleans and there is no "either" state to fall back on — so a suspended customer is only visible under the
filter the success toast names; and the urql document cache needs **both** `GraphQLUserActiveTbl` and
`GraphQLUsersActiveTblPage` in `additionalTypenames`, since a page with no rows carries only the second and the
table would not re-read itself after the last suspension on a page. Suspending goes through a `window.confirm`
naming the customer and the session end; enabling does not. `yarn test:cov` ends at 1071 tests over 71 files,
100 on all four metrics.

### E19-S05 — Anti-story: the customers table never queries an encrypted field   `not built` (deliberately — an anti-story)
⚠️ **A boundary to defend, not work to schedule** — the same shape as E02's anti-story. Nothing is built
by this story; it exists so the next person to look at the screen does not close the obvious gap in the
obvious way.

**What must not be added, and what happens if it is:**
- **A `search` argument matching a name, a city or a partial email.** `shopOwnersActiveTbl` builds
  `new RegExp('^' + escaped, 'i')` over `personalData.firstName`, `personalData.lastName` and
  `personalData.address.city`. On `user` all three are randomly encrypted, and random ciphertext preserves
  nothing — the regex compares against base64 and returns zero rows for every term, on every account. It
  does not error. It looks like a customer base with nobody in it.
- **A sort on any name or city column.** Same cause, different symptom: the rows come back in ciphertext
  order, which is stable, arbitrary, and indistinguishable from a working sort until somebody checks.
- **Switching one of those fields to deterministic "so the table can find it".** ADR-INDEX §4 already
  refuses this in the shop-owner direction and the reasoning is symmetrical: equal plaintext gives equal
  ciphertext, which is an equality oracle for anyone holding a read. The five deterministic fields are the
  ones a login or a verification link must *find*, and the list does not grow for convenience.
- **Leaving those fields in the clear on `user`, the way `shopOwner` leaves them.** That is the divergence
  `lib/schemas/user.js` documents deliberately — `shopOwner` pays for its operator table in plaintext, and
  `user` was designed not to have that bill. This epic's whole point is a table that does not incur it.
**Acceptance criteria:** none — nothing is built. The story is satisfied by the absence of a `search`
argument on `usersActiveTbl`, the absence of a second member in `UsersTblSortField`, and the absence of
any name or address column on the screen.
**Traces:** ADR-029; ADR-INDEX §4 (both encryption rows); `BEs/marketplace-db-setup/lib/schemas/user.js`.

**Outcome — held, and nothing was built.** The three absences it names are now asserted rather than merely
left out: the frontend suite fails if the screen grows a searchbox or a textbox, if it renders anything but its
four columns, or if a sort control appears on a column other than the registered date, and the router test
proves an invented `?search=` never reaches the GraphQL variables. Both places a `search` would have to be
written — the resolver and the lib query — carry the reasoning at the line it would go on, and
`lib/schemas/user.js` now refuses the "make just one field deterministic" exception in advance.

## 6. Open questions

| # | Question | Owner |
|---|---|---|
| 1 | Does disabling a customer need a recorded reason? `shopOwner` has operator-private `notes` and a `shopOwnerUpdateNote` mutation; `user` has no such field, and adding one means a schema change on the collection this epic otherwise leaves alone — and a decision on whether the note is encrypted like everything else on `user` or clear like the shop owner's | Platform owner |
| 2 | Does the operator dashboard need `usersStats` / `usersPerPeriod`, the way it has both for shop owners? Both are countable without touching an encrypted field, so neither is blocked by ADR-029 — they are simply not asked for yet | Platform owner |
| 3 | **Erasure has no path on any tier.** There is no `userDel`, no Admin counterpart to `shopOwnerDel`, and no self-service delete in `marketplace-dev-user-authenticated-resource`'s six mutations — a customer cannot close their own account and an operator cannot close it for them.
