## 1. Epic goal

Give the operator the two things they do not have over a customer account: **a list of them, and a
switch.** `marketplace-admin` has a shop-owners table, a categories screen and a session console; it has
no customers screen at all, and the Admin resource service has no `user*` operation of any kind.

⚠️ **The lever is a hole, not a feature request.** `user.disabled` already exists in the validator
(`account.js` `DISABLED`) and is already enforced everywhere it matters — `tryLoginUser` refuses the
login, `tokenInfoUser` refuses the session, `funUserUpdatePwd` refuses the password change. What is
missing is the only thing that could ever set it. Suspending a customer today means a write made by hand
against MongoDB, which is a production write nobody reviews, on the one collection encrypted whole.

⚠️ **The list is bounded by ADR-029, and stays inside it.** `user` is the collection with no operator
table, and `lib/schemas/user.js` says so in as many words — every personal field is encrypted precisely
*because* nothing sorts, searches or paginates customers. This epic does not reverse that: the table sorts
and filters on fields that were never encrypted, and the encrypted ones are displayed or not displayed,
never queried. See E19-S05, which is the anti-story that keeps it that way.

## 2. Scope

| In scope | Out of scope | Why |
|---|---|---|
| One compound index on `user`, in a new migration | Editing `20260301000300-create-user.js` | Migrations are immutable ([`CLAUDE.md`](../../../../CLAUDE.md)); the collection has exactly one index today, `login.email_unique` |
| `usersActiveTbl` — offset/limit, sort on `registeredAt`, filter on `disabled` / `deleted` / `emailVerify.valid` | A `search` argument of any kind | `shopOwnersActiveTbl`'s `search` builds `/^term/i` over first name, last name and city; all three are ciphertext on `user` and a prefix match against ciphertext returns nothing, silently |
| `userUpdateStatus` writing `disabled`, and revoking that customer's sessions | A `waitApprov` argument, or any second flag | Closed 2026-08-25 — `user` gets no approval gate, permanently (`epics/E07.md` §6, ADR-INDEX §4) |
| A `/customers` screen in `marketplace-admin` mirroring `TblShopOwners.tsx` | A customer detail page rendering `personalData` or `addresses[]` | Every one of those fields is PII the operator has no stated task for; R25 (GDPR applicability) is still open and this epic does not widen it |
| Truing up the four documents that currently say no operator table over `user` exists | Changing which fields are encrypted, or which algorithm any field uses | ADR-029 §4 — the deterministic list does not grow for convenience, and encrypting less is what the shop-owner row of ADR-INDEX §4 already refuses |
| — | `userDel`, and any erasure path | **None exists on any tier** — a customer cannot delete their own account either. That is a separate gap, raised in §6 rather than closed here |

## 3. Build state

**Not built — none of the six stories.** Verified against the working tree, not assumed:

- `BEs/dev/marketplace-dev-admin-authenticated-resource/src/graphQLApi/schema/mutations/` holds 21 files
  and **not one of them names `user`**: seven `shopOwner*`, four `company*`, two `item*`, three
  `itemCategory*`, `adminUpdatePwd`, two `keygrip*` and two `revoke*`. The queries directory has no `users*`
  entry either.
- `marketplace-admin/src/features/` holds `shopOwners`, `categories`, `security`, `dashboard`, `settings`
  and `login`. There is no `users` or `customers` feature, and no page under `src/pages/` names one.
- `user.disabled` has **five read paths across four services and no writer at all**: `tryLoginUser`
  (`marketplace-dev-public-authorization`), `tokenInfoUser`
  (`marketplace-dev-user-authenticated-authorization`), `funUserUpdatePwd`
  (`marketplace-dev-user-authenticated-resource`), and the two path maps `RESET_PWD_PATHS_USER` and the
  verify-email pair in `marketplace-dev-public-resource`, which hand the flag to the shared reset and
  confirmation flows. `epics/E07.md` §6 named the first three, which are the direct gates; the other two
  reach it through a field-name map and gate the same way. Nothing anywhere `$set`s it.
- `BEs/marketplace-db-setup/migrations/20260301000300-create-user.js` creates **one** index,
  `login.email_unique`. `shopOwner` has four `tbl_active_*` compound indexes it does not
  (`phase4/ERD.md:360`); none has a `user` counterpart.
- `BEs/marketplace-db-setup/lib/schemas/user.js` states the reason in the validator's own comment:
  "there is no operator table over this collection". That sentence is what E19-S06 has to amend, and it
  is amended by *narrowing*, not by deleting: there will be an operator table, and it still reads nothing
  encrypted.

## 4. Stories

Landing order is the story order: the index before the query that needs it, the query before the screen
that renders it, the anti-story alongside all three, the documentation last.

### E19-S01 — One compound index on `user`, in a new migration   `not built`
Technical story. Give `usersActiveTbl` an index to sort and page on, so the operator's first screen is not
a collection scan that grows with every signup.
**domains:** database, migrations
**Acceptance criteria:**
- A **new** migration file under `BEs/marketplace-db-setup/migrations/` creates
  `{deleted: 1, disabled: 1, registeredAt: -1, _id: -1}` on `user`, named `tbl_active_registeredAt` to
  match its `shopOwner` counterpart. `20260301000300-create-user.js` is not edited.
- ESR order, with `_id` as the tiebreak, for the same reason `phase4/ERD.md:360` gives on `shopOwner`:
  equality fields first, then the sort, then a unique tail so a page boundary cannot repeat or skip a row.
- Its `down` drops that index and nothing else.
- No field on `user` changes shape, type or encryption algorithm, so no database is rebuilt
  ([`CLAUDE.md`](../../../../CLAUDE.md) — a `lib/schemas/` change would have meant rebuilding every
  database that has run these migrations; this is not one).
**Traces:** `phase4/ERD.md` §Indexes; ADR-014 (migrations).

### E19-S02 — `usersActiveTbl` on the Admin resource service   `not built`
As an operator, I want a paginated list of registered customers, so that I can find the account a support
request is about without opening a database shell.
**domains:** backend, GraphQL, Admin tier
**Acceptance criteria:**
- New query in `marketplace-dev-admin-authenticated-resource` (port 4024 — a domain read, so the
  **resource** service, never the authorization one).
- Arguments mirror `shopOwnersActiveTbl` **minus `search`**: `offset: Int! = 0`,
  `limit: Int! = USERS_TBL_DEFAULT_LIMIT`, `sortDir: SortDirection! = DESC`, and filters for `disabled`,
  `deleted` and `emailVerify.valid`.
- `sortBy: UsersTblSortField! = REGISTERED_AT`, and the enum has **exactly one member**. It is an enum
  rather than a dropped argument so the client shape matches the shop-owner table and a second sortable
  clear field can be added without a breaking change — not because a second one is planned.
- The row carries `_id`, `login.email`, `registeredAt`, `disabled`, `deleted` and `emailVerify.valid`, and
  nothing from `personalData` or `addresses[]`.
- ⚠️ **`login.email` is returned but never ordered or matched by prefix.** It is deterministic, so the
  driver decrypts it on the way out and an *equality* lookup on it works — that is what makes "find the
  account for this address" possible. Deterministic ciphertext preserves equality and nothing else
  (ADR-029), so it sorts in ciphertext order, which is not alphabetical order and is not the operator's
  order either.
- The page total is counted under the same filter as the rows.
**Traces:** `phase4/API_CONTRACTS.md` §Admin resource — queries; ADR-029; ADR-002 (Admin tier = the
`admin` collection it authenticated against, not a role check).

### E19-S03 — `userUpdateStatus`, the missing writer   `not built`
As an operator, I want to disable and re-enable a customer account, so that a compromised or abusive
account can be stopped without a hand-written database update.
**domains:** backend, GraphQL, Admin tier, sessions
**Acceptance criteria:**
- New mutation in the same service: `_id: ID!`, `disabled: Boolean!`, answering `Boolean!` like the other
  twenty-one on this tier.
- **`disabled` is the only argument and it is `Boolean!`**, for the reason `shopOwnerUpdateStatus`
  documents: a nullable flag makes the mutation a partial update, and `null` for "leave alone" and `null`
  for "clear it" are the same wire value, so turning a flag *off* becomes inexpressible. There is no
  `waitApprov` counterpart and there will not be one.
- After the Mongo write lands — never before it — every session that customer holds is revoked, via a
  `endEveryUserSession` built the way `endEveryShopOwnerSession` is: `revokeAllSessionsForAccount` with
  `TIER.user`. ⚠️ **The tier constant is not incidental** — the session index is per tier, so
  `TIER.shopOwner` with a customer's `_id` reads an index that does not exist, deletes nothing, and
  reports success.
- Re-enabling revokes nothing: nobody's credentials changed, and logging a customer out as a *reward* for
  being re-enabled is not a control (E15-S07's rule, and the same reading `shopOwnerUpdateStatus` gives).
- The operator's own session is untouched — this is the cross-account revoke, not E15-S05's "the caller
  goes too", which is a rule about whose credentials changed.
- The residual is one access-token lifetime, as it is for `shopOwner`: refresh sessions die, an access
  token already issued keeps working until it expires. Closing that needs an access-token deny list, which
  this platform has deliberately not built.
**Traces:** E15-S06/E15-S07 (cross-account revoke); `phase5/SEQUENCE_DIAGRAMS.md` §2.8 (the shop-owner
shape this mirrors); ADR-002.

### E19-S04 — the `/customers` screen in `marketplace-admin`   `not built`
As an operator, I want the customers list and its enable/disable switch in the console I already use, so
that suspending an account is one click behind the same login as everything else.
**domains:** frontend, Admin SPA
**Acceptance criteria:**
- A feature directory `src/features/customers/` and a page under `src/pages/`, mirroring
  `TblShopOwners.tsx` / `ShopOwnersPage.tsx` in layout and in its pagination controls.
- Columns: email, registered date (`en-GB`, like every other date on this platform), and the status the
  three flags add up to. **No name column, no city column, no address column** — see E19-S05.
- The status control writes through `userUpdateStatus` and shows the row as disabled immediately after,
  including the fact that the customer's sessions have just ended.
- The screen has no free-text search box, and no sort control on any column but the registered date. An
  input that silently matches nothing is worse than an absent one.
- Nav entry alongside the shop-owners one; it is the operator's fourth surface, not a sub-page of a
  shop owner.
**Traces:** [`docs/frontends.md`](../../../frontends.md); E19-S02, E19-S03 (cannot precede either).

### E19-S05 — Anti-story: the customers table never queries an encrypted field   `not built`
⚠️ **A boundary to defend, not work to schedule** — the same shape as E02's anti-story. Nothing is built
by this story; it exists so the next person to look at the screen does not close the obvious gap in the
obvious way.

**What must not be added, and what happens if it is:**
- **A `search` argument matching a name, a city or a partial email.** `shopOwnersActiveTbl` builds
  `new RegExp('^' + escaped, 'i')` over `personalData.firstName`, `personalData.lastName` and
  `personalData.address.city`. On `user` all three are randomly encrypted, and random ciphertext preserves
  nothing — the regex compares against base64 and returns zero rows for every term, on every account. It
  does not error. It looks like a customer base with nobody in it.
- **A sort on any name or city column.** Same cause, different symptom: the rows come back in ciphertext
  order, which is stable, arbitrary, and indistinguishable from a working sort until somebody checks.
- **Switching one of those fields to deterministic "so the table can find it".** ADR-INDEX §4 already
  refuses this in the shop-owner direction and the reasoning is symmetrical: equal plaintext gives equal
  ciphertext, which is an equality oracle for anyone holding a read. The five deterministic fields are the
  ones a login or a verification link must *find*, and the list does not grow for convenience.
- **Leaving those fields in the clear on `user`, the way `shopOwner` leaves them.** That is the divergence
  `lib/schemas/user.js` documents deliberately — `shopOwner` pays for its operator table in plaintext, and
  `user` was designed not to have that bill. This epic's whole point is a table that does not incur it.
**Acceptance criteria:** none — nothing is built. The story is satisfied by the absence of a `search`
argument on `usersActiveTbl`, the absence of a second member in `UsersTblSortField`, and the absence of
any name or address column on the screen.
**Traces:** ADR-029; ADR-INDEX §4 (both encryption rows); `BEs/marketplace-db-setup/lib/schemas/user.js`.

### E19-S06 — True up the four places that say this surface does not exist   `not built`
Technical story. Four documents and one source comment currently state, correctly for today, that no
operator table exists over `user`. Building E19-S02 makes each of them false in one clause and true in the
rest, and each has to be narrowed rather than deleted — the encryption decision they explain does not
change, only the claim that nothing reads the collection from the Admin tier.
**domains:** documentation
**Acceptance criteria:**
- `BEs/marketplace-db-setup/lib/schemas/user.js` — the validator's "there is no operator table over this
  collection" becomes the narrower, still-true statement: the operator table reads no encrypted field, so
  every personal field stays encrypted for exactly the reason it always was.
- [`docs/data-model.md`](../../../data-model.md) §`user` divergence 2 — "nothing writes it" stops being
  true when E19-S03 lands, and points at `userUpdateStatus`.
- `phase4/API_CONTRACTS.md` — one query row and one mutation row on the Admin resource tables; the
  mutation count in that section's "All seventeen answer `Boolean!`" line is already stale by four and is
  recounted rather than incremented.
- `phase4/ERD.md` §Indexes — the new `user` index joins the table that today lists four on `shopOwner` and
  one on `user`.
- `phase2/BOUNDED_CONTEXT.md` BC-07 — the ⚠️ paragraph added on 2026-08-25 says the lever is unbuilt; it
  says built, and names the mutation.
**Traces:** `phase5/DEFINITION_OF_DONE.md`; E18's precedent — the epic that records what the others did.

## 5. Dependencies

- **E19-S01 → E19-S02 → E19-S04.** The index before the query that pages on it, the query before the
  screen that renders it. E19-S03 depends only on the service existing and could land first; it is placed
  second because a lever with no list is a mutation nobody can reach from the UI.
- **Needs `revokeAllSessionsForAccount`** from `marketplace-common` (E15) and `TIER.user` — both exist and
  are already consumed by the shop-owner path in this same service.
- **Repos touched:** `marketplace-db-setup` (S01), `marketplace-dev-admin-authenticated-resource` (S02,
  S03), `marketplace-admin` (S04), the parent workspace (S06's documents). Four sub-repos plus the parent,
  so five commits by ADR-031's N+1 rule, landing `marketplace-db-setup` first.
- **Blocks nothing.** No other epic waits on this one.
