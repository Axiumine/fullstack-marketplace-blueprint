## 1. Epic goal

Make the auth boundary's *refusals* as well tested as its acceptances, and make the documents stop describing a
platform that does not exist. Coverage here is 100% on four metrics with mutation score 100, and the tier
rejection path is still untested in two of three resource services — because a fully covered happy path can sit
next to an unexercised guard and the numbers stay green. This epic closes that, closes the audit's remaining
blind spots, and leaves behind a checklist so the next audit costs less than this one did.

## 4. Stories

### E18-S01 — Every resource service proves it rejects the wrong tier   `built 2026-08-13`
**As a** platform, **when** a valid session for one tier is presented to another tier's resource service,
**I want** a test in *that service* proving the 403 **so that** a refactor of its middleware cannot silently
open it.
**domains:** backend, testing
**Acceptance criteria:**
- `marketplace-dev-authenticated-resource` and `marketplace-dev-admin-authenticated-resource` each gain a
  reject-path test modelled on
  `marketplace-dev-user-authenticated-resource/test/authorizationAuthenticatedResourceHandler.test.mts:52-89`,
  asserting the 403 and the response body shape, not merely a non-200
- Each service also tests the **missing-tier** case — a session hash with no `tier` field — asserting it is
  refused rather than treated as a wildcard, which is ADR-004's whole point
- The tests drive the service's own handler, not `assertTier` directly; a test that calls the shared helper
  does not prove the service reaches it
- `yarn test:cov` stays 100/4 and `yarn test:mutation` stays 100 in both services with no threshold changed and
  no exclusion added
**Traces:** NFR-SE01, NFR-SE02, NFR-SE05, NFR-MA01, NFR-MA02; ADR-002, ADR-004; BCON-01, BCON-02
**Evidence (gap):** no equivalent test file in either service's `test/` directory

**Evidence (built): satisfied, and this epic did not build it.** The story was written on 2026-08-10 against
a workspace where one service tested the reject path. Verified 2026-08-13: all three resource services now
carry `test/authorizationAuthenticatedResourceHandler.test.mts`, and every criterion above is met by tests
that landed with the tier discriminator itself (`2f8257b` in `marketplace-dev-authenticated-resource`,
"refuse a foreign-tier access token, and prove it") rather than under this epic.

| Service | Wrong tier | No tier | 403 not 401 |
|---|---|---|---|
| `-authenticated-resource` | `it.each([['admin'], ['user']])` | `refuses a session with no tier at all` | `extensions.http.status` asserted `403` |
| `-admin-authenticated-resource` | `it.each([['shopOwner'], ['user']])` | same | same |
| `-user-authenticated-resource` | `it.each([['shopOwner'], ['admin']])` | same | same |

All three drive `authorizationAuthenticatedResourceHandler()(ctx, next)` — the service's own middleware, not
`assertTier` — and assert `ctx.state.user` stayed `undefined` and `next` was never called, so a handler that
threw *after* populating state would fail them. The missing-tier case is refused by `actual !== expected`
with no branch of its own, which is what makes a tier-less session fail closed rather than act as a wildcard
(ADR-004). Each suite additionally pins that the introspection bypass cannot rescue a foreign-tier token —
`does not let the introspection code rescue a bearer token from another tier` — which is the hole the two
mechanisms would otherwise leave between them.

**Gates:** unchanged, because no source or test changed to close this. `marketplace-dev-authenticated-resource`
— 182 tests, coverage 100% on all four metrics (180/180, 49/49, 48/48, 176/176).
`marketplace-dev-admin-authenticated-resource` — 647 tests, 100/4 (597/597, 213/213, 137/137, 550/550).
`marketplace-dev-user-authenticated-resource` — the reference implementation, unchanged since E15-S05.

⚠️ **What this story left open was E18-S02, and this story is the reason it exists.** Three suites agreeing

### E18-S02 — The auth boundary is tested the same way in every service   `built 2026-08-13`
State plainly: the reason one service had the test and two did not is that there is no shared expectation of
what an auth-boundary test suite must contain.
**domains:** backend, testing, documentation
**Acceptance criteria:**
- A written contract lists the cases every authenticated service's boundary suite must cover: valid session
  accepted, wrong tier refused, missing tier refused, absent token refused, malformed token refused, expired
  session refused, and — once E14 lands — replayed token refused
- Every one of the seven authenticated services has a test file covering all cases in the contract; a
  meta-test or a documented checklist enumerates the services and fails when one is missing a case
- The contract lives in `docs/testing.md` next to the existing vitest layout, not in an epic file
- The `INTROSPECTION_CODE` path gets the same treatment: accepted with the right code, refused with a wrong
  one, refused with none
**Traces:** NFR-SE01, NFR-SE02, NFR-SE05, NFR-MA01, NFR-MA02, NFR-MA05; ADR-004; BCON-01, BCON-02, BCON-03
**Evidence (gap):** three resource services, three different boundary-test shapes

**Evidence (built).** Eleven cases, `AB-01`..`AB-11`, live in
`BEs/marketplace-common/src/others/authBoundaryContract.mts` — the list, a per-service exemption map with a
written reason for every excusal, and `requiredAuthBoundaryCases(service)`. Each of the seven authenticated
services carries a `// AB-xx:` comment above the test that proves the case and a
`test/authBoundaryContract.test.mts` that reads its own boundary suite and fails on a missing tag. The whole
contract is written up in [`docs/testing.md`](../../../testing.md), *The auth-boundary contract* — the table,
the seven-service enumeration and the exemptions.

**Open question 1 is answered: a meta-test, but a per-repo one.** Each service scans only its own `test/`
directory, so no service reads another's files and BCON-05 is not strained; the only shared thing is the
case list, which travels the way every other shared thing does, as a `marketplace-common` export. A service
the contract has never heard of cannot ask what it owes — `requiredAuthBoundaryCases` throws rather than
answering an empty list, which is what makes a new service's suite fail until somebody writes its row.

| Service | Cases | Notes |
|---|---|---|
| `-authenticated-resource` | 10 | AB-07 excused — mints no token |
| `-admin-authenticated-resource` | 10 | same |
| `-user-authenticated-resource` | 10 | same |
| `-authenticated-authorization` | 11 | gained AB-07 and AB-11 |
| `-admin-authenticated-authorization` | 11 | same |
| `-user-authenticated-authorization` | 11 | same |
| `-authenticated-logout` | 8 | AB-02/AB-03 excused — serves all three tiers (ADR-005) and asserts none; AB-07 excused |

⚠️ **The contract found two real holes, both in the three authorization services**, which is the answer to
whether an exercise like this is bookkeeping. **AB-11** — the `INTROSPECTION_CODE` environment allowlist of
E13-S11 — was tested in the four other services and in none of these three. **AB-07** — the replay refusal of
E14-S02 — was asserted only from the writing side: `refresh.test.mts` proved the tombstone was *written* and
nothing proved a replayed token was *refused* or its family revoked. Both are now covered: the new test
drives the handler with a token whose session is gone and whose tombstone is older than the ten-second grace
window, and asserts the lineage read, one `del` per member with the family set deleted last, and the ordinary
498 the caller gets — a replayer learns nothing from the response about whether the revocation happened.

⚠️ **A tag is a claim the scanner cannot check.** It catches the case nobody wrote a test for, not a tagged
test gutted while its tag stayed; that one is caught by mutation testing, one gate later. The scanner was
verified non-vacuous by renaming a tag and watching the suite fail, and each file asserts it read a non-empty
suite and a non-empty case list.

**Gates:** every touched repo at 100% on all four coverage metrics, no threshold changed and no exclusion
added. `marketplace-common` — mutation 100.00, 55 mutants on the new module, all killed.
`-user-authenticated-resource` 363 tests · `-authenticated-resource` 193 · `-admin-authenticated-resource` 658
· `-user-authenticated-authorization` 143 · `-authenticated-authorization` 167 ·
`-admin-authenticated-authorization` 143 · `-authenticated-logout` 141, the four authorization-and-logout

### E18-S03 — The env-var contract is asserted, not assumed   `built`
State plainly: E16-S06 removes an env var from five services. Nothing currently fails if a required var is
dropped from the list, or added to the list and never read.
**domains:** backend, testing
**Acceptance criteria:**
- Each of the nine services has a test asserting its `REQUIRED_ENV_VARS` array with `toStrictEqual` against an
  exact expected list — not a length check, which passes on a swap
- A test proves the service fails to start when a required var is absent, for at least one var per service
- No test, fixture or snapshot in this story reads or prints a value from `.env`; only the committed `env`
  templates and the variable **names** appear anywhere
- `marketplace-dev-public-authorization`'s expected list has 16 entries today and whatever E16-S06 leaves it
  with afterwards
**Traces:** NFR-AV01, NFR-SE12, NFR-MA01, NFR-MA02, NFR-MA05, NFR-CO01; BCON-01, BCON-02
**Evidence (gap):** `BEs/dev/marketplace-dev-public-authorization/src/index.mts:26-46`
**Outcome (2026-08-13):** Nine services, nine exact lists, asserted in each `test/index.unit.test.mts`:
admin-authorization 16 · admin-resource 24 · shopOwner-authorization 16 · logout 13 · shopOwner-resource 23 ·
public-authorization **15** · public-resource 14 · user-authorization 16 · user-resource 15. The criterion
expected 16 for public-authorization "and whatever E16-S06 leaves it with afterwards"; E16-S06 has landed and
left it 15. The order is asserted along with the membership, which the criterion did not ask for: the boot
reports the *first* missing variable, so a reordering changes which name an operator is sent to look for.
Eight of the nine gained a `start (missing environment)` test — public-resource already had one — proving
`start()` rejects with neither `RedisConnect` nor `disconnectAllDatabases` called, because a boot abandoned
half-open leaves a handle the pool goes on holding. admin-resource asserts `Internal Server Error` rather
than the variable name, since its `checkRequiredEnv` raises through `throwInternalError` and keeps the name
in `extensions.description`.

⚠️ **The story also fixed a silent exit 0**, which no criterion named. `checkRequiredEnv()` runs outside
`start()`'s `try`, so a missing variable propagated to the entrypoint's `.catch` — and that handler held one
`Sentry.captureException(e)` and nothing more. With no DSN configured the SDK discards the event, Node ran
out of work, and the process left with a **success** code: a service that never bound its port was
indistinguishable, to Docker and to any restart policy reading `$?`, from one asked to stop. It now writes
to stderr and calls `process.exit(1)`. The edit sits inside the `v8 ignore` entrypoint tail, below every
`mutate` line range in the stryker configs, so no range moved and no gate shifted.

**Acceptance criteria:**

- The finding names every dependency that participates in the auth path — `@axiumine/koa-utils`, `keygrip`,

  backlog are constrained by what those packages do
- The finding states which dependencies are external-and-unmodifiable from this workspace, so future epics stop

- Anything actionable becomes a story; anything accepted becomes a `RISK_REGISTER` row
**Traces:** NFR-SE06, NFR-SE08, NFR-MA05, NFR-MA07, NFR-CO01; BCON-01, BCON-04
**Evidence (gap):** audit §5 — "No full dependency-tree audit was performed."

**Outcome (2026-08-13):** [`docs/report/dependency-tree-advisory-scan.md`](../../../report/dependency-tree-advisory-scan.md).
Fifty-four advisories match installed versions across the fourteen repos that have a dependency tree —
`marketplace-nginx` and the parent workspace have none. Twenty-nine reach a production zone and twenty-eight
a toolchain zone, and every one of the twenty-nine is either `@socketlabs/email`'s pinned `axios@0.21.4` or a
transitive of `@apollo/server`. None is reachable through an attacker-influenced path: the SocketLabs client
is built with a hard-coded endpoint URL and no proxy, so the SSRF, `NO_PROXY`-bypass, proxy-credential-leak
and prototype-pollution classes have no way in, and the two that remain need the SocketLabs API host itself

`koa@3.2.1`, `redis@6.2.0`, `@sentry/node@10.69.0`, `@axiumine/koa-utils@6.0.0`, none carries an open
advisory — and every one of them except `@axiumine/marketplace-common` is external and unmodifiable from this
workspace, which the finding states once so the next epic stops rediscovering it.

⚠️ **Two things the story's own framing did not anticipate.** First, `yarn audit` cannot answer this question
in this workspace at all: yarn 1 aborts the entire run when any package fails to resolve, and
`@axiumine/marketplace-common` is unpublished by design — so the finding reads the tree from `node_modules`
and queries npm's bulk advisory endpoint directly. Second, the vulnerable `axios` ships into **eight**
services and is loaded by **one**; the other seven declare `@socketlabs/email` — a peer of `koa-utils` — and
never import the module that uses it. That is a dependency to delete seven times, not a vulnerability to
patch. Three stories opened (E18-S10..S12), **R49** opened for the residual, and **R21** rewritten.

### E18-S05 — Investigation: what encryption at rest actually covers   `built`
State plainly: ADR-029's CSFLE encrypts specific fields with per-collection DEKs. It is not a statement about
the storage layer, and the two are routinely confused.
**domains:** database, documentation
**Acceptance criteria:**
- A written finding lists every field currently encrypted through `encryptedFields.mts`'s `KEY_ALT_NAMES`, and
  every field carrying personal data that is **not**, with a reason per omission
- The finding states plainly whether the underlying MongoDB and Redis volumes are encrypted at rest in Dev and
  whether that is known for any other environment — and says "unknown" where it is unknown
- The finding covers Redis, whose session values are not personal data but whose keyspace is credentials until
  E13-S01 lands
- The result either closes the audit §5 item or becomes a story with an owner
**Traces:** NFR-SE06, NFR-SE07, NFR-MA05, NFR-CO01, NFR-CO02; ADR-029; BCON-01, BCON-04
**Evidence (gap):** audit §5 — encryption at rest named as adjacent and unexamined
**Outcome (2026-08-13):** [`docs/report/encryption-at-rest-coverage.md`](../../../report/encryption-at-rest-coverage.md).
**30 field paths across 4 of the 6 collections, under 4 DEKs, 5 of them deterministic** — enumerated per
collection with the algorithm and what each holds. The not-encrypted half is written down for the first time,
in three groups: the three `shopOwner` fields ADR-029 traded away for the operator table's sort and prefix
search; the hashes, gates and lifecycle timestamps that are either not personal data or unencryptable by
construction (`addresses.[]._id` and `defaultAddress` would make the `$expr` validator unsatisfiable — every
write to `user` refused); and `company`, where fourteen fields describe an entity or are published to
anonymous visitors. **Storage: no, and the binary cannot.** MongoDB is Community 8.0.28 (`"modules": []`) and
`mongod --help` matches `encrypt` **zero** times — WiredTiger encryption is Enterprise-only, so it is absent
rather than unconfigured. Both volumes are on plain XFS with **zero dm-crypt devices** on the host. Unknown
for every other environment, because no other environment exists; no backup mechanism exists either, so that
question has no answer yet rather than a bad one.

⚠️ **Two of this story's own premises were wrong and the finding says so.** Redis session values **are**
personal data — the access-token hash carries the account's `email` in plaintext, which R45 already records
for traffic in transit and nothing recorded at rest, where it lands in the AOF and outlives the session's TTL
until a rewrite compacts it. And the keyspace is **not** credentials any more: E13-S01 has landed, every
session and tombstone key is a digest, and only the pre-cutover read fallback can still reach a raw-token key
— which E13-S10 deletes. The audit §5 item is closed; the residual is carried as **R48** rather than as a
story, because there is no code to own — the decision belongs to whoever provisions the production host
ADR-032 still owes.

### E18-S10 — Seven services stop shipping an email client they never call   `built`
State plainly: `@socketlabs/email` is a peer of `@axiumine/koa-utils`, and eight services declare it directly.
One imports the module that uses it. The other seven install `axios@0.21.4` — 23 advisories, 10 of them High —

**domains:** backend
**Acceptance criteria:**
- `@socketlabs/email` is removed from `dependencies` in the seven services that do not reach it:
  `admin-authenticated-authorization`, `admin-authenticated-resource`, `authenticated-authorization`,
  `authenticated-logout`, `authenticated-resource`, `public-authorization`, `user-authenticated-authorization`
- `marketplace-dev-public-resource` keeps it — it imports `@axiumine/koa-utils/email/SocketLabsLib` in four files
- Each removal is verified by the service's own gates passing, not by inspection
- ⚠️ **The env contract is corrected in the same story, because it is backwards.** `authenticated-resource`
  (`src/index.mts:47-48`) and `admin-authenticated-resource` (`src/index.mts:48-49`) require
  `SOCKETLABS_SERVER_ID` and `SOCKETLABS_SERVER_APIKEY` and never construct the client; `public-resource`, which
  does, requires neither — and `SocketLabsLib` reads the key into a template literal, so an unset variable becomes
  the string `"undefined"` and fails at the first registration email instead of at startup. Both entries are
  removed from the two services that do not send mail, and `public-resource` gains every variable
  `SocketLabsLib`'s constructor actually reads — `SOCKETLABS_SERVER_ID`, `SOCKETLABS_SERVER_APIKEY`,
  `PLATFORM_NAME`, `APP_DOMAIN`, `EMAIL_FROM` — plus `APP_DOMAIN_USER`, which its own call sites pass. E18-S03's
  `toStrictEqual` assertions are updated in the same commit
- A re-run of the scan shows `axios` absent from those seven trees
**Traces:** NFR-SE08, NFR-MA05, NFR-MA07; BCON-01
**Evidence (gap):** [`dependency-tree-advisory-scan.md`](../../../report/dependency-tree-advisory-scan.md) §4.1

**Outcome (2026-08-13).** Eight repos, eight commits, every criterion met. `@socketlabs/email` left
`dependencies` in the named seven; `public-resource` kept it and is now the only tree in the workspace that
reaches `axios@0.21.4`. The mail credential pair left `REQUIRED_ENV_VARS` and the committed `env` template in
`authenticated-resource` and `admin-authenticated-resource`, and left the `env` template of the five services
that never required it either. `public-resource` gained the six its client actually reads, in one block with
the argument written beside it. Each service's own gates ran on its own commit — lint, typecheck, coverage at
100, Qodana — and E18-S03's `toStrictEqual` lists moved with the code: 23 → 21, 24 → 22, 14 → 20.

⚠️ **`yarn install` cannot run in any of these repos, and this is the same fact that made `yarn audit`
useless in E18-S04.** `@axiumine/marketplace-common` is published to neither the LAN mirror nor npmjs — both
answer 404 — and yarn 1 aborts the entire resolution over one unresolvable package, so no lockfile in this
workspace can be regenerated by the tool that wrote it. The seven `yarn.lock` files were therefore pruned by
a rewriter that computes reachability from the manifest exactly as yarn would, emits every surviving block
verbatim, and was proven byte-identical against an untouched control repo before being pointed at anything.
Each dropped 38 lines and six blocks, all deletions: `@socketlabs/email`, `axios`, `follow-redirects`,
`promise-retry`, `retry@0.12.0`, `err-code`. `retry@0.13.1` stays in all nine on an unrelated path — the
service that never declared SocketLabs carries it too, which is what makes that safe to say.

⚠️ **The directories are still on disk.** Reachability is now false for all seven — the scan reads it from
the manifests — but nothing has physically pruned `node_modules`, and nothing can until an install can run.
A deployment built from these manifests will not carry the closure; this machine's checkout still does.

⚠️ **Three things this story did not expect, all of them findings rather than side effects.**
- **`APP_DOMAIN_USER` is absent from this machine's environment file.** The new check found it the first time
  the integration suite booted the service. `sendUserVerifyEmail` reads it directly, so every customer
  verification link built on this machine has carried the string `undefined` — a defect that had no symptom
  at startup and would have had one only in a customer's inbox. The variable is in the committed template; it
  is the real file that lacks it, which is exactly the gap a startup contract exists to close.
- **The integration suite now pins all six itself** — `.invalid` hosts and a placeholder key — rather than
  borrowing whatever the developer's environment holds. That suite deliberately avoids the two paths that
  really send, and a run that fell back to the live credentials was one edit away from sending for real.
- **Six variables in the two resource services are still required and read nowhere.** `EMAIL_FROM`,
  `DEV_TEAM_EMAIL` and `PLATFORM_NAME` are read only by `SocketLabsLib`, which those services do not import;
  `SAMESITE_COOKIE`, `HIT_STATS` and `REDIRECT_DOMAIN` appear in no reachable module at all — not in `src/`,
  not in either `@axiumine` package's `dist/`. They were left alone rather than removed on the same argument,
  because "reads it nowhere today" and "was never meant to" are different claims and only the first is
  measured. **E18-S13** carries them.
