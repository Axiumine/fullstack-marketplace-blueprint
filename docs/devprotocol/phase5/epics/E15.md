## 1. Epic goal

Make an account able to reach its own sessions. Today nothing in this platform can answer "which sessions
does this account have open?", so nothing can end them: changing a password leaves every stolen session
alive, disabling a ShopOwner leaves them logged in, and `logout` — the one deliberate teardown that exists —
was a silent no-op in production because it read a field name that was never written. This epic fixed the
broken logout first (E15-S01, 2026-08-12), then builds the account→sessions index that every other teardown
needs, then wires the credential and account-state writes to use it.

### E15-S02 — Every login and rotation records the session under its account   `built 2026-08-13`
State plainly: an account must be able to enumerate its own live sessions without scanning the keyspace.
**domains:** backend, testing
**Acceptance criteria:**
- Login and rotation both `hSet` one field into `${REDIS_KEY}idx:<tier>:<accountId>`, whose **field name** is
  the hashed session identifier produced by E13's `hashSessionToken` and whose value carries no token
  material; a unit test asserts the field name matches `/^[0-9a-f]{64}$/` and that the value's key set is
  exactly the agreed non-secret set
- The index key itself is `expire`d to `SESSION_CAP_DAYS_REMEMBERED` (E14-S05) on every write — the **longer**
  of the two caps, unconditionally, whatever cap the session being written carries. An abandoned index then
  cannot outlive every session it names, and a 30-day remembered session cannot outlive the index that names
  it. Using the session's own cap would be tighter and wrong: one 1-day login after a 30-day one would pull
  the whole key's TTL down to a day and orphan the remembered session — a live session listed nowhere, which
  E15-S04's revocation would then silently miss. E15-S03 prunes fields that outlive their sessions; nothing
  in this epic recovers a session that outlives its index entry, so the TTL must never be the shorter number
- `SCAN`, `KEYS` and any glob-matching command appear nowhere in the diff — `grep -rniE '\b(scan|keys)\(' `
  over the change returns zero hits (BCON-08: a Redis cluster makes keyspace scanning both wrong and slow)
- One unit test per writer asserts the exact `hSet` and `expire` arguments; Stryker 100 in every touched
  package with no threshold change
**Traces:** NFR-SE01, NFR-SE05, NFR-SC02, NFR-SC03, NFR-MA01, NFR-MA02; ADR-003, ADR-004; BCON-01, BCON-08
**Evidence (gap):** no `idx:` key shape exists anywhere in `BEs/`

**Evidence (built):** one helper, two writers, and the whole contract sits in the helper —
`indexSession(store, prefixedRefreshToken, refreshTokenData)` in
`marketplace-common/src/others/sessionKeys.mts`, beside `sessionKey` and `hashSessionToken`, so no call
site builds an index key or a field name out of a template literal. It takes the whole `IRefreshData`
rather than a tier and an id: tier, account id and mint time then come from one object and no caller can
pair a tier with a stranger's id.

The value is `{ tier, mintedAt }`, decided by the platform owner on 2026-08-13, and **`mintedAt` is the
lineage's `originalLogin`, not the current token's mint time** — rotation carries it forward unchanged, so
a session refreshing every fifteen minutes reads as a login from when the customer actually logged in.

⚠️ **The two writers order the index write differently, and both orders are deliberate.** In rotation
(`refreshSessionTokens.mts`) it sits after the pair's two `expire`s and before the family `sAdd`, so a
failed index write rolls back while the **old refresh token is still alive** — the client keeps a working
session instead of one whose successor was never recorded. In login (`setRedisLoginSession.mts`) it is
last inside the `try` and its failure fails the login: a session that cannot be listed is a session
E15-S04 can never revoke, so a half-made login is worse than none. That rollback deletes the two session
keys and *not* the index field — what it leaves is a row naming keys that no longer exist, a stale listing
and never a credential, and E15-S03's per-field TTL is what removes it.

**The TTL is the literal 2 592 000 in every test, never the constant.** `SESSION_INDEX_TTL_SECONDS` is
derived from `SESSION_CAP_DAYS_REMEMBERED × MILLISECONDS_PER_DAY / 1000`; a test importing it would agree
with the constant about any value, including a mutated one. The login fixture carries
`sessionCapDays: '1'` precisely so the assertion proves the key still gets thirty days.

BCON-08 verified directly: `grep -rniE '\b(scan|keys)\('` over both diffs returns only `Object.keys` — a
JS built-in, in tests. No Redis keyspace-scanning command appears anywhere in the change.

**Gates:** `marketplace-common` — 617 tests, coverage 100% on all four metrics (622/622, 274/274, 121/121,
577/577), `yarn test:mutation` **100.00** with `sessionKeys.mts` at 51 mutants and `refreshSessionTokens.mts`

### E15-S03 — The index prunes itself   `built 2026-08-13`
State plainly: an index that only ever grows becomes both a memory leak and a lie about which sessions are
live — pruning is part of the feature, not a follow-up.
**domains:** backend, testing
**Acceptance criteria:**
- Rotation removes the superseded field with `hDel` in the same routine that adds the successor
  (`refreshSessionTokens`), and `logout` removes its own field; both asserted with exact arguments
- Fields whose sessions expired without passing through rotation or logout are removed by **`HEXPIRE`, a
  per-field TTL** — decided 2026-08-10, see below. Every `hSet` into the index is followed by an `HEXPIRE`
  on that field whose value is the **remaining time to `originalLogin + sessionCapDays`** (E14-S05), not the
  session key's own Redis TTL and not the index key's; both unit tests assert the two commands and their
  exact arguments
- **Rotation does not reset the field TTL.** The cap is absolute from the original login, so the successor
  field is written with the remaining cap the predecessor carried, computed from the same `originalLogin`. A
  test rotates a session close to its cap and asserts the successor field's `HPTTL` is the remainder rather
  than a fresh full cap — otherwise a rotating session is listed as live for ever
- **Upper bound on stale fields per account: zero by design** — a field cannot outlive the session it names
  by more than Redis's own expiry latency, because the TTL is the cap itself. Demonstrated by an integration
  test that writes a field with a one-second TTL, waits, and asserts both `hKeys` and `HTTL` no longer see it;
  a second assertion proves a live field's `HTTL` equals the cap remainder
- `HEXPIRE` is a single-key command and the index key is one key, so BCON-08 holds; the `hSet` and the
  `HEXPIRE` address the same key and may share one pipeline. No command in the diff takes more than one key —
  asserted the same way E15-S02 asserts the absence of `SCAN` and `KEYS`
- The Redis floor this requires — **7.4.0 or newer, Redis proper** — is recorded in
  [`docker-DBs/README.md`](../../../../docker-DBs/README.md) §Redis and pinned by `docker-DBs/env`. The story
  still carries a startup version check that fails loudly rather than assuming the floor holds
- The chosen mechanism is written into `docs/data-model.md` alongside the other Redis key shapes, in the same
  commit — no undocumented key shape survives this epic (BCON-03)
**Traces:** NFR-SE05, NFR-PE02, NFR-SC02, NFR-MA01, NFR-MA02, NFR-MA05; BCON-01, BCON-03, BCON-08
**Evidence (gap):** none — the index does not exist yet; this criterion exists so it is not built without it

> **Decided 2026-08-10: `HEXPIRE`, not a lazy prune.** The two are not interchangeable implementations of one
> idea, which is what the choice looked like when it was written down. **A lazy prune asks the wrong
> question.** Its liveness test is *does the session key still exist*, and after E14-S05 a session key can
> exist while the session it holds is already dead: the key carries the sliding 90-day `REFRESH_TOKEN_EXPIRY`
> from `@axiumine/koa-utils`, but the session is refused at its absolute cap of one day, or thirty when
> remembered. A prune built on key existence therefore keeps naming sessions nobody can use — and E17 renders
> that list to an operator, who would be looking at logins that cannot log in. A field TTL set to the cap
> expires the entry when the session stops working, which is the property actually wanted, enforced by Redis
> rather than by a read path remembering to run.
>
> **The rest follows the same way.** Lazy prune costs `hKeys` plus one `EXISTS` per field plus an `hDel` per
> corpse on *every* read — every revoke and every console render — against one extra single-key write command
> per login. Its stale-field bound is not zero but "logins in thirty days" for an account that never revokes
> and never opens the console, since nothing prunes an index nobody reads. And it is the larger test surface:
> a branch, a dangling-field fixture, and a proof that its cleanup never batches into a multi-key `del`.
>
> **What it costs, recorded so a later reversal is a decision rather than a discovery.** The platform can
> never run on a Redis without hash-field TTLs. That is free today — dev-only, self-hosted, pinned at
> `7.4-alpine`, floor written into `docker-DBs/README.md`. **Valkey is explicitly not a supported target**
> (decided 2026-08-10), so its command coverage is not a constraint on this choice and no compatibility layer
> is owed to it. If some future deployment genuinely cannot offer hash-field TTLs, the lazy prune returns as
> a code change and not a config flag — because of the predicate difference above, the two mechanisms are not
> drop-in for one another.

**Evidence (built):** the field TTL and the cap refusal are **one expression, read by two callers** —
`sessionCapDeadline(originalLogin, sessionCapDays)` in `marketplace-common/src/others/sessionLifetime.mts`,
where `resolveAuthorizationSession` already computed the instant a session stops being honoured. Two copies
of that arithmetic could drift by a rounding, and both directions fail silently: a row outliving its session
is a listing an operator cannot act on, a row dying first is a live session listed nowhere. Its second half,
`sessionCapRemainingSeconds`, **rounds up and floors at one second** — early expiry is the orphan E15-S02's
key TTL exists to prevent, and Redis reads a non-positive hash-field TTL as "delete now", which is right for
a session already past its cap but the wrong shape for a caller to depend on.

`indexSession` now writes three commands in one order — `hSet`, then `expire(key, 2_592_000)`, then
`hExpire(key, field, remaining)` — and **the two TTLs are deliberately different numbers on the same write**:
thirty days for the key, whatever is left of *this* session's cap for the field. `unindexSession` is the
mirror, and rotation calls it **after** `deleteSession`, never before: the other order leaves a usable
refresh token listed nowhere for as long as the delete takes. Every rotation suite asserts that order with
`invocationCallOrder`, not by reading the source.

**Rotation does not reset the field TTL** because the successor is written from the predecessor's
`originalLogin`, which E15-S02 already carried forward. Nothing new enforces it; the tests pin a clock an
hour after login and assert `30 * 86_400 - 3_600` as a literal, so a mutant that swaps `originalLogin` for
`Date.now()` dies.

⚠️ **`assertHashFieldTTLSupport` exists because Redis refuses an unknown command at the first call, not at
startup.** Without it a service boots on a 7.2 server, verifies every token it is handed, and dies inside
the first login of the day with the cause three layers below the symptom. It probes with `hTTL` — read-only,
single-key — on the connection the service will actually use, before anything else touches it, and the four
authorization services assert exactly that with `invocationCallOrder` against `loadKeygrip`. The logout
service does not carry it: `hDel` has existed since Redis 2.0. `up.sh --with-redis` checks the container's
version independently, because the probe only sees whatever `REDIS_URL` points at.

**The three rotation suites had been agreeing with a write they never asserted.** Since E15-S02 their mocked
`redisClient` happened to expose `hSet` and `expire`, so `indexSession`'s write passed through unremarked;
adding `hExpire` turned that silence into four hard failures. The fix asserts the whole index write — key,
field name, JSON value, count raised to four — rather than adding the missing mock and moving on.

Live proof rather than a mocked one: the integration suite in `marketplace-dev-public-authorization` writes
a field with a one-second TTL against the real cluster, waits, and asserts `hKeys` and `HTTL` both stop
seeing it, then asserts a live field's `HTTL` is the cap remainder. BCON-08 holds by inspection —
`hExpire`, `hTTL` and `hDel` each take one key, and the diff adds no multi-key command.

- `marketplace-common` `yarn test:cov` 100/4, `yarn test:mutation` 100, then `./deploy-local.sh` before any

**Evidence (gap):** no revocation routine exists in `BEs/marketplace-common/src/others/`

**`sessionKeyFromIndexField` is the piece that was missing, and it belongs in `sessionKeys.mts`** —
nothing on this platform may build a session key out of a template literal, and a revocation has to build
one from a field. It is the only key builder here that takes no token, because a field *is* the body of
the key that filed it; the test asserts the round trip against `sessionKey(TOKEN)` rather than against a
string, so a second digest or a stray namespace word cannot slip in. That failure would be a revocation
reporting success having deleted nothing.

⚠️ **The index key is deleted last, and the order is the recoverability.** The index is the only record of
what remains to be deleted: a process death between the two, with the index gone first, leaves live refresh
tokens nothing can name — unlistable, unrevocable, alive to their cap. This way round the worst residue is
an index naming keys that are already gone, which is what makes an interrupted revocation safe to simply
run again. Asserted as an order, not a call set.

empty family set still deletes its key. A family set has no per-field TTL and would accumulate one dead set
per login; an index hash has one on every field (E15-S03), and Redis drops a hash the moment its last field
goes. Tidying it would be a write issued on the strength of a guess.

BCON-08 holds by assertion rather than by reading: every `hKeys` and every `del` call is checked to carry
exactly one argument, so `del(...keys)` — which passes on this single node and is refused across slots on a
cluster, *after* the caller has been told the account is logged out — cannot pass this suite.

### E15-S05 — Changing a password ends every session   `built 2026-08-13`
**As a** customer who has just changed their password because I fear my account is compromised, **when** the
mutation succeeds, **I want** every session including the attacker's gone **so that** the change is the
remedy it appears to be.
**domains:** backend, database, testing
**Acceptance criteria:**
- Each of the three tiers' password-change mutations calls `revokeAllSessionsForAccount` after a **successful**
  Mongo write and never before it; a unit test per tier asserts the revoke is not called when the update
  reports `matchedCount === 0` or throws
- **The calling session is revoked with the rest** — no exemption, no re-issue: after a successful password
  change the caller's own next request is refused and it must log in again. A unit test per tier asserts the
  caller's session is among the revoked ones rather than leaving it emergent
- The caller's **access-token key is deleted too, not only its refresh key** — a revoke that drops the refresh
  key alone leaves the caller working until the access token expires naturally, which makes the decision
  above cosmetic for exactly the window an attacker is still inside. Tested by asserting both of the caller's
  keys are absent from Redis after the mutation returns
- The mutation's own failure mode is stated: if the revoke throws after the password write succeeded, the
  request fails loudly rather than returning success with sessions still live; tested by making the Redis
  double throw
- Per-service `yarn test:cov` 100/4 and `yarn test:mutation` 100
**Traces:** NFR-SE01, NFR-SE03, NFR-SE05, NFR-MA01, NFR-MA02, NFR-CO01; ADR-002, ADR-003; BCON-01, BCON-02
**Evidence (gap):** audit §3.3 — no credential mutation imports `redisClient`

> **Decided 2026-08-10: the calling session is revoked too.** The alternative was to exempt the caller and
> keep them signed in, which is friendlier and is what a fair number of products ship. It was rejected because
> it defeats the one scenario the feature exists for: the user changing a password because they believe
> someone else is inside the account cannot tell which of the live sessions is theirs, and neither can the
> server — an exemption is granted to *whichever session sent the mutation*, and an attacker who has the
> victim's password can send it. "Revoke all but me" is therefore not a weaker version of "revoke all"; it is
> a rule an attacker can aim at. Revoking everything makes the outcome the same no matter who calls it.
>
> **The exemption also cannot be built honestly here.** The routine is `revokeAllSessionsForAccount` — one
> input, `{ tier, accountId }`, four callers (E15-S04). Sparing the caller means a fifth parameter carrying a
> session identity into a routine whose whole point is that callers cannot get the shape wrong, plus a branch
> per call site that E17's operator-triggered revoke must then always pass as false. The uniform rule keeps
> the routine one-shaped and keeps its test surface finite.
>
> **What it costs, recorded so a later reversal is a decision rather than a discovery.** A password change is
> now a logout on every device, including the phone the user is holding. The three frontends must treat the
> refusal that follows as "log in again", not as an error state — no story in this epic owns that screen, and
> it is written here so it is not met for the first time in production. If the friction proves unacceptable,
> the reversal is a product decision that re-opens this question, not a patch to the routine.

**Evidence (built):** `endEverySession(ctx)` in `src/lib/auth/endEverySession.mts` of
`marketplace-dev-user-authenticated-resource` and `marketplace-dev-admin-authenticated-resource`, called
from `userUpdatePwd.mts` and `adminUpdatePwd.mts` respectively. A one-line helper per service rather than
the routine called inline, because the call is not one call: the account's refresh sessions go through
`revokeAllSessionsForAccount`, and then the caller's *access* key — which no index names — goes through
`deleteSession`. Inlining that pair at four future call sites is how they drift apart.

⚠️ **"Three tiers" in the acceptance criteria is two, and the third is not an omission.**
`marketplace-dev-authenticated-resource` (ShopOwner) has **no password-change mutation at all** — a shop
owner's password is set at registration and recovered through the public reset flow, and there is nothing
on that tier for this story to hook into. `grep -rl 'UpdatePwd' BEs/dev/*/src/graphQLApi/schema/mutations/`
returns exactly the two files above. When a ShopOwner self-service password change is built, it inherits
this story's rule and its four tests, which is why the helper is a named file and not an inline pair.

⚠️ **The public reset-password flow is an uncovered credential write, and it is outside this epic's
landing order.** `marketplace-dev-public-resource` writes a new password in `resetPwdFlow.mts` and
`resetPwdFlowUser.mts` (koa-utils `createResetPwdFlow`) for ShopOwner and User respectively, and neither
calls the routine. That is the same defect this story fixes, on the path a compromised account is *most*
likely to take — the person who has lost control of their password is the person using the reset link.
Recorded here rather than fixed silently: widening S05 to a fourth service was not the scope asked for.
**It needs a story of its own before this epic closes.**

**Order and residue, asserted rather than assumed.** Refresh sessions first, the caller's access key
second. A process death between the two leaves the caller's access token alive for the minutes it has
left — exactly the residual every *other* device already carries, since an access key is a digest of a
string no index can name. The reverse order leaves the refresh sessions alive, and refreshing one is how
the intruder mints a fresh access token. Both of the caller's key shapes are deleted, digest and raw, so
a session minted before E13's cutover dies with the rest.

**The call sits after the write and inside the `try`, both load-bearing.** Before the write, a change that
then failed validation would have logged the account out of every device for nothing. Outside the `try`, a
Redis that refused would leave the mutation answering `true` with every stolen session still live — the
exact lie the story exists to stop telling — so a failed revoke fails the mutation as a 500 the caller can
retry. Tested per tier by making the double throw.

**Gates:** `marketplace-dev-user-authenticated-resource` — 354 tests, coverage 100% on all four metrics,
`yarn test:mutation` **100.00** over 506 mutants. `marketplace-dev-admin-authenticated-resource` — 625
tests, coverage 100/4 (593/593, 209/209, 136/136, 547/547), `yarn test:mutation` **100.00** over 1097
mutants. One survivor was killed rather than tolerated on the way: `ctx.request.header?.authorization`

**Answered:**

- *What non-secret fields does an index entry carry?* — **`tier` and `mintedAt`, and nothing else**, decided
  2026-08-13 by the platform owner, carried by E15-S02. The field *name* is the session digest and already
  identifies the session; the value exists only so E17 can render a row without ever holding a token. `tier`
  is what lets a caller rebuild the session key from the digest; `mintedAt` is what makes the row readable to
  a human deciding which session to end. **One half of that turned out to be wrong once built** (E15-S02):
  the key to rebuild is `${REDIS_KEY}${field}` and needs no tier at all, because the tier is in the *index
  key's own name*. `tier` stays in the value on the second reason alone — a row E17 can render without
  parsing a key name — and the pair was agreed as a pair. **`familyId` and the cap were offered and refused**: both are E14
  lineage state that rotation already maintains on the session hash, and duplicating them here would mean two
  writers keeping one truth in step across every rotation. Nothing device- or network-derived is in the set,
  so the standing GDPR decision needs no exception for this key.
- *`waitApprov`: enforce, or correct the document?* — **enforce**, and it was already enforced: E01-S11 built
  the gate on 2026-08-12 while this question was open. Closed 2026-08-13 by E15-S08, which found the only
  document still claiming the gap was this epic. Reasoning on the story, including why it does not reopen
  ADR-002.
- *Does a password change revoke the calling session too?* — **yes**, decided 2026-08-10, **built by E15-S05
  on 2026-08-13** on both tiers that have a password-change mutation, with a test per tier asserting the
  caller's own session is among the revoked ones rather than leaving it emergent. Inherited by E15-S06.
- *Stale-field pruning: `HEXPIRE` or lazy prune?* — **`HEXPIRE`**, decided 2026-08-10, **built by E15-S03 on
  2026-08-13**. Redis 7.4 floor recorded in [`docker-DBs/README.md`](../../../../docker-DBs/README.md)
  §Redis, checked by `up.sh --with-redis` and by a boot probe in each of the four authorization services;
  **Valkey is not a supported target**, decided the same day.
