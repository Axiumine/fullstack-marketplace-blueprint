## 1. Epic goal

Give the operator a window onto sessions and signing keys, and two blunt levers — revoke this session, revoke
this account's sessions — without ever putting a credential on a screen. This epic renders what E15 and E16
already enforce; it adds no security control of its own, because a control that fires when a human notices
something is not a control.

## 2. Scope

| Item | In/Out | Why |
|---|---|---|
| Read-only session list per account | In | closes the operator half of audit §3.6b |
| Revoke one session / revoke all of an account's sessions | In | the levers; both call E15's routine |
| A reuse-event trail — what was revoked, when, why | In | reuse detection (E14) that nobody can see is hard to act on |
| Key-custody screens over E16's resolvers | In | E16 ships resolvers; this ships the screen |
| Displaying a token, a token prefix, a key or a key prefix | **Explicitly out, permanently** | stated by the user as a condition of this epic existing |
| Any detection that depends on an operator looking | **Explicitly out** | detection lives in the hot path — E14, E15, E16 |
| A tenth deployable service for admin session tooling | Out | see E17-S09 |
| Anything network- or device-derived on a session row | Out | the standing GDPR decision — no IP, not truncated, not hashed, not salted |

## 4. Stories

### E17-S01 — The Admin schema slice describes sessions and keys before any type is generated   `built`
State plainly: this repo's types are generated **from** hand-written schema slices. Running codegen before
editing the slice produces nothing and reads as a broken toolchain.
**domains:** frontend, backend
**Acceptance criteria:**
- `marketplace-admin/schema/admin-authenticated-resource.graphql` is edited by hand to add the session and
  key-custody types, queries and mutations, and **then** `yarn codegen` is run — the generated file is a build
  output of that edit, and the commit contains both
- A `GraphQLReuseEventAction` enum lives in its own file on the backend side and is referenced by both the
  schema slice and the resolver, so the frontend's generated union and the backend's runtime values cannot
  drift; a test asserts the two value sets are equal
- The session type carries no field named for, or capable of holding, a token; a test enumerates its fields
  against an exact expected set (BCON-01)
- `yarn lint` and `yarn typecheck` pass in `marketplace-admin` with no generated file edited by hand
**Traces:** NFR-MA01, NFR-MA05, NFR-CO01; BCON-01, BCON-03
**Evidence (gap):** `marketplace-admin/schema/admin-authenticated-resource.graphql` has no session types

**Outcome — built.** The slice was edited by hand and `yarn codegen` run afterwards; the commit carries the
slice and `src/gql/adminResource/` together, because the generated file is a build output of that edit and a
commit holding one without the other describes a tree that does not type-check. `GraphQLReuseEventAction`
has its own file on the backend (`src/graphQLApi/schema/types/GraphQLReuseEventAction.mts`) and its values
come from `REUSE_EVENT_ACTIONS` in `marketplace-common` rather than being spelled twice; `test/schema.test.mts`
imports that constant and asserts `enumValuesOf('GraphQLReuseEventAction')` equals it, so the union the
frontend generates and the strings the backend writes into Redis cannot drift. The field sets are asserted
exactly, not by snapshot: `fieldsOf('GraphQLSession')` is `['id', 'tier', 'mintedAt', 'familyId']` and
`fieldsOf('GraphQLReuseEvent')` is `['familyId', 'tier', 'accountId', 'action', 'at']`, with a second test
refusing thirteen banned names (`token`, `refreshToken`, `accessToken`, `cookie`, `secret`, `hash`, `digest`,
`ip`, `ipAddress`, `remoteAddress`, `userAgent`, `device`, `location`) and a third asserting nothing on either
type is nullable. **By name rather than by snapshot on purpose** — a snapshot answers a field added later by
asking to be updated, and that update looks like every other one.

### E17-S02 — An operator can list the sessions an account holds   `built`
**As a** platform operator investigating a report of a compromised account, **when** I open that account,
**I want** its live sessions listed **so that** I can see how many there are and end them.
**domains:** backend, frontend, testing
**Acceptance criteria:**
- A `sessions(tier, accountId)` query in `marketplace-dev-admin-authenticated-resource` reads E15's
  `${REDIS_KEY}idx:<tier>:<accountId>` hash with `hGetAll` and returns one row per field, carrying the session
  id, its tier, its mint time and its family id — and nothing derived from a network address
- A test drives the resolver against a seeded index and asserts the serialised response, as a string, contains
  neither the seeded refresh token nor the seeded access token — a substring check, not a shape check
- The resolver runs Admin-tier only through `assertTier`, and **its reject path has its own test**, not just
  its accept path
- Stale index fields — sessions whose keys have already expired — are not rendered as live; the resolver either
  filters them or E15-S03's prune has already removed them, and a test covers whichever it is
**Traces:** NFR-SE01, NFR-SE02, NFR-SE05, NFR-MA01, NFR-MA02, NFR-CO01, NFR-CO02; ADR-002, ADR-004; BCON-01, BCON-08
**Evidence (gap):** no session query exists in the Admin resource service

**Outcome — built.** `sessions(tier, accountId)` reads E15's index with one `hGetAll` on one key — never
`SCAN`, never `KEYS` (BCON-08) — and returns one `GraphQLSession` per live field carrying `id`, `tier`,
`mintedAt` and `familyId`. Two things came out differently from the criterion's wording, both stricter:

- **The row is built from the session hash, not from the index entry.** The index value carries its own copy
  of the tier and the mint time, so a row assembled from both records can disagree with what the platform
  actually authenticates against after a failed rotation. The index answers one question — *which* sessions
  exist — and every displayed field comes from the session itself. `funSessions` says so at the definition.
- **Stale fields are filtered, and the read does not prune.** `hGetAll` on a vanished session answers `{}`,
  which is the whole detection, and the field is left in place: this is a read, and a read that writes is a
  read that needs its own rate limit and its own audit line. E15-S03's TTL is what removes it.

`id` is the index field — the SHA-256 of the *prefixed* refresh token — and the argument for publishing it is
written on `ISessionRow`: every raw-token key is built as `${REDIS_KEY}access:…` or `${REDIS_KEY}refresh:…`,
so a bare digest names no live key and replays as nothing, and `revokeSession` uses it only to name a key of
an account the caller already named. Rows are sorted newest-first with the id as tie-break, because Redis
returns hash fields in no order and a table that reshuffles between polls cannot be clicked safely. `assertTier`
runs Admin-only with **both** paths tested, and `test/sessionNoLeak.test.mts` asserts the serialised response
contains neither the seeded refresh token nor the seeded access token as a substring.

### E17-S03 — An operator can end one session   `built`
**As a** platform operator, **when** I revoke a single session, **I want** its two tokens gone and its index
row gone **so that** the list I am looking at stays true.
**domains:** backend, testing
**Acceptance criteria:**
- `revokeSession` deletes the session's keys with one single-key `del` each (BCON-08) **and** removes the
  session's field from the account index with `hDel` in the same routine — an index row surviving its session
  is the defect this criterion exists to prevent
- Revoking an already-dead session succeeds without throwing and still prunes the index field; tested
- The mutation is rate-limited through `assertUnderRateLimit` with no network-derived bucket key
- An integration test seeds a real session, revokes it through the resolver, and asserts the next authenticated
  call on that session's tier is refused; every seeded key registered at creation and drained in `afterAll`
  (BCON-09)
**Traces:** NFR-SE01, NFR-SE03, NFR-SE05, NFR-MA01, NFR-MA02; ADR-003; BCON-01, BCON-08, BCON-09
**Evidence (gap):** no revoke resolver exists

**Outcome — built.** `revokeSession` is one single-key `del` on the session key plus one `hDel` on the
account's index (BCON-08), and **both run always** — the index field is pruned even when the session was
already gone, which is the case that repairs the operator's list rather than an error. It answers `false`
there instead of throwing, so the console can say "already ended" rather than "ended", and the frontend does
exactly that. The order is load-bearing and written down at the definition: **session key first, index field
second.** A crash between the two leaves a row naming a key that no longer exists, which the next call
cleans up and which grants nobody anything; the reverse order leaves a live session listed nowhere —
invisible to the operator *and* to E15-S04's revocation, alive until its own cap.

Metering is `guardSessionWrite`, a bucket per operator **per operation** at 60/hour off the Redis session's
account id and nothing network-derived: `app.proxy` is off on every service here, so an address-keyed
counter would be one global bucket the whole platform spends — the per-address half of rate limiting is the
edge's, in `conf.d/20-rate-limit.conf`. The integration test seeds a real session, revokes it through the
resolver and asserts the next authenticated call on that tier is refused, with every seeded key registered at
creation and drained in `afterAll` (BCON-09). One residual is recorded rather than fixed: **the access token
minted from a revoked refresh session keeps working until its own expiry** — minutes — because only refresh
sessions are indexed, and closing that gap means an access-token deny list this platform has deliberately not
built. ⚠️ **The second half of that sentence stopped being true on 2026-08-13** (v1.3): the refresh hash now
carries `accessKey`, the key of the access session minted beside it, so ending an access token needs one
`hGet` and one `del` rather than a deny list. ~~The residual itself stands — revocation still reads no such
field — and is **R54**.~~ ⚠️ **And the first half stopped being true hours later** (v1.4): `funRevokeSession`
reads that field and deletes the access session before the refresh one, so the operator's revoke ends the
whole login. **R54** is closed. What the console promises changed with it, and the unit suites are where the
new order is pinned; the integration test still asserts the keyspace it always did, and a session seeded
without an `accessKey` exercises exactly the "carries no bound key" branch.

### E17-S04 — "Log out everywhere" is safe against a login that arrives mid-revoke   `built`
State plainly: revoking every session reads the index, deletes what it found, then wants to delete the index
key — and a login landing between the read and that delete would have its index row destroyed while its
session stayed live, leaving an invisible session. That is the concurrency defect this story exists to close.
**domains:** backend, testing
**Acceptance criteria:**
- After the revoke loop, the routine **re-reads** the index. The index key is deleted only if its field set is
  unchanged; otherwise the routine `hDel`s exactly the fields it revoked, and repeats over the new ones
- The retry is bounded by a named constant and, on exhaustion, leaves the index key in place rather than
  deleting it — an orphaned field is recoverable, a destroyed index is not; tested at the bound
- A test simulates the race directly: the mock adds a field between the first `hKeys` and the delete, and the
  test asserts the index key was **not** deleted and the newcomer's field survived
- The same routine backs E15-S05's password-change teardown — one implementation, two callers, asserted by
  both call sites' tests referencing it
**Traces:** NFR-SE01, NFR-SE03, NFR-SE05, NFR-MA01, NFR-MA02, NFR-MA05; BCON-01, BCON-02, BCON-08
**Evidence (gap):** E15-S04's routine as first designed had no re-read; this story is the correction

**Outcome — built, as a correction to a routine that had already landed.** E15-S04's
`revokeAllSessionsForAccount` in `marketplace-common` shipped without the re-read, so this story went in as a
fix commit against it rather than as new code. After the revoke loop the routine re-reads the index with
`hKeys`; the index key is `del`eted only if the field set is unchanged, and otherwise it `hDel`s exactly the
fields it revoked and goes round again on whatever appeared. The bound is `REVOKE_INDEX_REREAD_ATTEMPTS = 3`
— named, asserted, and argued at its definition: each round is a full revoke of what the previous round did
not know about, so a login must land inside three consecutive rounds to survive, while *unbounded* would let
an account being logged into in a loop spin this routine inside a request. **On exhaustion the index key is
left in place**, holding the fields that were not revoked — an index naming a live session is recoverable and
a deleted index is not — and the returned count is what was actually revoked, so a caller reporting "N
sessions ended" never counts a session that is still open. The race is tested directly: the fake store adds a
field between the first `hKeys` and the delete, and the test asserts the index key was **not** deleted and the
newcomer's field survived.

One implementation, now **four** callers rather than the two the criterion names: `funRevokeAllSessions` (this
console), `endEverySession` and `endEveryShopOwnerSession` in the Admin resource service, and the user
service's own `endEverySession` — E15-S05's password-change teardown among them. Both call sites named in the
criterion assert against it by name in their own tests.

### E17-S05 — Reuse events are recorded and readable   `built`
**As a** platform operator, **when** a refresh token is replayed and a family is revoked, **I want** to see
that it happened **so that** a silent mass logout is explainable rather than a mystery ticket.
**domains:** backend, frontend, testing
**Acceptance criteria:**
- E14-S03's family revocation appends an event carrying the family id, the account, the action from
  `GraphQLReuseEventAction` and a timestamp — and **no token, no token hash preimage, and no network data**
- The event store has a stated retention and a stated bound on growth; a test proves the bound
- A query exposes the events to Admin tier only, with its `assertTier` reject path tested
- A test asserts the serialised event response contains no substring of the token that triggered it
**Traces:** NFR-SE01, NFR-SE02, NFR-SE05, NFR-MA01, NFR-MA02, NFR-CO01, NFR-CO02; ADR-002, ADR-004; BCON-01
**Evidence (gap):** E14-S03 revokes silently as designed

**Outcome — built.** Both `revokeSessionFamily` call sites in `marketplace-common` now file one line through
`recordReuseEvent`: the lineage id, the tier, the account id, an action from `REUSE_EVENT_ACTIONS`, and `at`
as epoch millis carried as a string. Five fields, and a test asserts the stored line's key count so a sixth
cannot be added quietly. **No token, no digest of one, no prefix of one, nothing network-derived** — the
contract is written on `IReuseEvent`, and `funReuseEvents` strips nothing because nothing needing stripping is
ever written.

Store and retention answer §6's first two questions: **a capped Redis list**, one key per account
(`reuse:<tier>:<accountId>`), written with three single-key commands in the only order that keeps the bound
true at every instant — `lPush`, then `lTrim` to `REUSE_EVENTS_MAX = 50`, then `expire` at
`REUSE_EVENTS_TTL_SECONDS`, which is E15's own `SESSION_INDEX_TTL_SECONDS` — **30 days from the last append**,
so a trail still being written to does not age out mid-incident and cannot outlive the sessions it describes
by an interval nobody chose. A fake list proves the bound. **A revocation is never conditional on the append
landing**: the caller records *after* revoking, because a store that refuses leaves sessions ended and an
operator without an explanation, while the other order would leave a trail claiming a logout that never
happened — an explanation that is wrong is worse than silence.

The vocabulary is two values, one per call site — `refreshTokenReplayed` (E14-S02/S03) and `sessionCapReached`
(E14-S05) — and the account comes off the tombstone, which gained `_id` and `tier` for this: by replay-
detection time the session hash is gone. A marker written before that change still revokes and only loses its
event. `reuseEvents(tier, accountId)` reads with one `lRange` over one key, newest first, with the reject path
of `assertTier` tested alongside the accept path, and `test/sessionNoLeak.test.mts` asserts the serialised
response holds no substring of the token that triggered the event.

confirmation text verbatim and assert that **refusing it fires no mutation at all**, which is the criterion's
real content. Coverage came out at 100 on all four metrics with the new route included and no threshold
touched.

### E17-S07 — The console cannot leak a credential, and a test proves it every run   `built`
State plainly: "we agreed not to display tokens" is a convention. This story makes it a gate.
**domains:** backend, frontend, testing
**Acceptance criteria:**
- One test in the backend and one in the frontend seed a known token value and a known key value, exercise
  **every** query and mutation this epic adds, and assert the serialised response of each contains neither —
  a loop over the resolver list, so a resolver added later without the check fails the suite
- No component in the new routes renders a value read from a field capable of holding key or token material;
  enforced by the field-set assertions in E17-S01 and E16-S07
- No new log statement in this epic's diff interpolates a session or key value; asserted by a grep-shaped
  check over the diff
**Traces:** NFR-SE01, NFR-SE02, NFR-SE04, NFR-SE05, NFR-SE12, NFR-MA01, NFR-MA02, NFR-CO01; BCON-01, BCON-02
**Evidence (gap):** nothing prevents it today because nothing exists today

**Outcome — built as two loops, one per side.** The backend's is
`marketplace-dev-admin-authenticated-resource/test/sessionNoLeak.test.mts`: it seeds a known refresh token, a
known access token and a known signing key, drives **every** field this epic adds, and asserts the serialised
response of each holds none of them as a substring. The frontend's is
`marketplace-admin/test/features/security/noLeak.test.tsx`, a `it.each` over a `SECURITY_OPERATIONS` list of
all seven — `KeygripStatus`, `Sessions`, `ReuseEvents`, `RevokeSession`, `RevokeAllSessions`, `KeygripRotate`,
`KeygripRetire` — asserting for each that `document.body.textContent` contains no secret and that
`JSON.stringify(call.variables)` contains none either. Three things make it stronger than a shape check:

- **The fixtures carry secrets in fields no document selects** — `keys[].value`, `holders[].secret`,
  `session.refreshToken`, `session.signingKey`, `reuseEvents[].presentedToken`. urql hands `data` through
  verbatim, so this proves the *screens* select nothing dangerous rather than proving the server sent nothing.
- **A control test asserts the app really is authenticating** — every recorded call carries
  `Bearer access:<token>` — so "sends no token" cannot pass by the app being broken.
- **A coverage test walks both screens once and asserts the observed operation-name set equals
  `SECURITY_OPERATIONS`**, which is what makes an eighth operation added later fail the suite instead of
  slipping past the loop. That is the criterion's "a resolver added later without the check fails the suite",
  moved to the layer where the omission would actually happen.

The "grep-shaped check over the diff" is a `readFileSync` scan asserting none of the eight touched sources
contains `console.` — deterministic, and it survives Stryker's sandbox because it asserts a property no
mutation introduces. The no-credential-rendered criterion is held by E17-S01's and E16-S07's exact field-set
assertions, as written.

### E17-S08 — Key custody is operable from the console   `built`
**As a** platform operator, **when** I need to rotate or retire a signing key, **I want** to do it from the
console **so that** rotation is a routine act rather than a deploy.
**domains:** frontend, testing
**Acceptance criteria:**
- The panel lists keys by id, state and timestamps only, renders rotate and force-retire behind confirmation,
  and surfaces E16-S04's "no key matched" error as a visible failure rather than a silent success
- Retiring the `current` key is not offered in the UI at all, matching E16-S04's server-side refusal — tested
- The stated propagation window from E16-S02 is shown next to the actions, so an operator is not misled into
  thinking a retire is instantaneous
**Traces:** NFR-SE04, NFR-US01, NFR-US02, NFR-MA01, NFR-CO01; BCON-01
**Evidence (gap):** E16-S07's resolvers have no consumer

**Outcome — built.** `KeygripPanel` lists every key by `id`, `createdAt` and `ageDays` and nothing else —
`GraphQLKeygripKeyInfo`'s field set is asserted to be exactly `['id', 'createdAt', 'ageDays']`, so the value
is not merely unrendered, it is not in the type. A fourth **State** column marks row 0 `Signing` in bold and
gives every other row a `Retire` button, which is how "retiring the current key is not offered in the UI at
all" is implemented: `keys[0]` *is* the signing key, so the offer is structurally absent rather than disabled,
matching E16-S04's server-side `KEYGRIP_RETIRE_CURRENT` refusal instead of relying on it. Rotate and retire
both sit behind `window.confirm`, and E16-S04's `KEYGRIP_RETIRE_UNKNOWN` surfaces as a visible `Toast`
failure — the success banner is gated on `error === undefined` **and** the `true`, which is not redundant:
GraphQL allows data and errors in one answer, and a confirmation shown under that error would tell an operator
a compromised key is gone while every service still verified with it.

The propagation window is rendered next to the actions as `PROPAGATION_WINDOW`, and it carries **the measured
number, not the poll ceiling**: 37 ms observed to all five signing services (E16-S09 §3), with
`KEYGRIP_POLL_MS = 300_000` named as the fallback for a lost pub/sub message. Quoting five minutes on the
screen would have been the safe-looking choice and the misleading one — an operator retiring a compromised key
needs to know it has already happened, and an operator who was told "up to five minutes" learns to distrust the
number the first time they check.

### E17-S09 — The decision not to add a tenth service is written down   `built`

a recorded reason, and the reason is operational cost, not an architectural prohibition.
**domains:** documentation
**Acceptance criteria:**

## 6. Open questions

| # | Question | Owner | Answer |
|---|---|---|---|
| 1 | Where do reuse events live — a Mongo collection with a TTL index, or a capped Redis structure? Mongo gives retention and query; Redis keeps the write on the hot path cheap. E17-S05 needs one answer. | Platform dev | **A capped Redis list**, one key per account, trimmed to `REUSE_EVENTS_MAX = 50` on every append. The write sits inside replay detection, on the refresh path, and a Mongo insert there buys a query nobody issues: the trail is read whole, newest first, by one console screen. The bound then holds *by construction* rather than by a sweep that has to be scheduled and could be skipped. |
| 2 | Retention for reuse events. Long enough to investigate, short enough not to become its own data-protection surface. | Platform owner | **Thirty days from the last event, not from the first** — `expire` is reissued on every append, so a trail still being written to cannot age out mid-incident. The figure is E15's own `SESSION_INDEX_TTL_SECONDS`, reused rather than reinvented, so a trail cannot outlive the sessions it describes by an interval nobody chose. |
| 3 | Does an operator need to see sessions across *all* accounts, or only per account? The investigation this console serves starts from a report about *an account*, and the platform-wide question — "how many sessions exist" — is a metric, not an operator action. |
| 4 | Should a revoke by an operator be attributable — which Admin did it? That is a second audit trail with its own retention question. | Platform owner | **Not attributable, for now.** `REUSE_EVENT_ACTIONS` holds two values, both machine-detected, and the constant's own comment says an operator's revocation is deliberately not a third — adding one would answer this question by accident. What exists instead is the rate-limit bucket, which is keyed on the operator's account id and hashed, so it meters without becoming a list of which operator ended whose sessions. Reopening this means a second store with its own retention decision, not a value in this enum. **This covers the session-revoke resolvers only** — `funRevokeSession` and `funRevokeAllSessions` write no operator id anywhere, which is what makes the answer true. Key custody, shipped by E17-S08 in this same epic, does the opposite: see question 5. |
