## 1. Epic goal

Make a copy of the session store useless to whoever gets it, and write down the four decisions this platform
made without recording. Today every access and refresh token is a Redis **key name**, so a dump, an `MONITOR`
tap, a slow-log entry or an AOF file is a list of live credentials in plain text. Hashing the key namespace
costs one `sha256` per lookup and turns all of those into a list of digests. The rest of the epic is a
documentation debt that four separate audit findings all trace back to.

## 4. Stories

### E13-S01 — Session keys are digests, not credentials   `built`
**As a** platform operator, **when** someone obtains a Redis dump, an AOF file or a `MONITOR` transcript,
**I want** it to contain no string that can be presented as a token **so that** a store compromise is not
immediately a session compromise.
**domains:** backend, testing
**Acceptance criteria:**
- `marketplace-common` exports `hashSessionToken(value)` returning a lower-case SHA-256 hex digest, exported
  from `package.json`, with a test asserting a known input maps to its known digest and that the output matches
  `/^[0-9a-f]{64}$/`
- **It is a named wrapper over E12-S11's `sha256Hex`, not a second digest helper.** E12 lands first, so the
  primitive already exists; if the order is ever reversed this story writes it and E12-S11 imports it.
  `grep -rn "createHash" BEs/marketplace-common/src` returns exactly one hit either way — two copies of a
  hashing helper is how the encodings end up disagreeing
- Every session key construction in the workspace goes through it — `grep -rnE '\$\{[A-Za-z_.]*REDIS_KEY\}\$\{' BEs/`
  returns zero hits where the interpolated value is not a `hashSessionToken(...)` result
- The **refresh** key hashes the value `verifySignedRefreshToken` returns, prefix included — not the raw cookie
  value; a test asserts the hashed input is the prefixed string, since hashing the wrong one produces a key
  that never matches and a platform that never authenticates
- The `REDIS_KEY` prefix stays exactly as it is — shared across all nine services (CON-04, settled) — so the
  single logout service still matches by token content alone (ADR-005, CON-05, settled)
- `marketplace-common` `yarn test:cov` 100/4 and `yarn test:mutation` 100
**Traces:** NFR-SE01, NFR-SE03, NFR-SE05, NFR-SE06, NFR-MA01, NFR-MA02; ADR-003, ADR-005; BCON-01, BCON-02, BCON-08
**Evidence (gap):** `BEs/marketplace-common/src/others/resolveAuthorizationSession.mts:70`

### E13-S02 — The cutover does not log anybody out   `built`
State plainly: on the deploy that flips key shapes, every session in Redis is stored under an old-shape key and
every request arrives asking for a new-shape one. Without a cutover, that deploy logs out every user on the
platform at once.
**domains:** backend, testing
**Acceptance criteria:**
- Reads try the hashed key first and fall back to the raw key; writes always use the hashed key; deletes remove
  **both** shapes, each with its own single-key `del` (BCON-08). One test per path asserts the exact call
  sequence
- **Every fallback path is behind one exported dated constant, `DUAL_READ_REMOVE_AFTER`, and its value is
  the cutover deploy date plus 90 days** — decided 2026-08-10. Not a boolean flag: a flag that
  defaults to on is indistinguishable from permanent code, and nobody audits a `true`
- **The clock starts at the deploy, not at the merge or the decision.** A raw-shape key can be written up to
  the instant the last service carrying the old writer is replaced, so the constant is set when the cutover
  reaches production and is not a value chosen in advance
- **`BGREWRITEAOF` is run on every node once the last old-shape writer is gone, and the runbook says so.**
  Production runs `appendonly yes` (§3), and an append-only file keeps every `HSET` that ever created a raw
  session key regardless of whether the key still exists — so without this the cutover changes what Redis holds
  and nothing about what the file on disk holds. Per node, not once against the cluster: a rewrite is local to
  the node that serves it. The runbook states plainly what this pass does **not** achieve — a rewrite emits the
  current dataset, so raw-shape keys that are still live are written back out in raw shape, and the residue is
  only fully gone at E13-S10. It is still worth running here because it clears every already-expired and
  already-deleted session, which is the bulk of the file
- A test asserts the current date is **before** `DUAL_READ_REMOVE_AFTER` and fails once it is not — the same
  forcing function E12-S05 uses against the Sentry major. A deliberately self-breaking test is the point:
  the alternative is a fallback nobody removes, and CI failing loudly on a known date is the cheapest
  reminder that exists
- **The fallback counts its own hits**, so removal is evidence rather than arithmetic: one counter
  incremented when a read misses the hashed key and finds a raw one. It records a count and nothing else —
  no key, no token, no identifier. E13-S10 removes the fallback only once that counter has been zero across
  a full window, because a non-zero count on day 90 means something is *still writing* old-shape keys and
  deleting the fallback would log those sessions out
- **Why 90 days, and what it is anchored to:** `REFRESH_TOKEN_EXPIRY = 90 * 24 * 60 * 60` in
  `@axiumine/koa-utils/dist/lib/tokens.mjs` is the physical Redis TTL on the longest-lived key, so a raw
  refresh entry can survive exactly that long regardless of what E14-S05's caps are signed off at. The
  number therefore does not depend on that sign-off — but if either the koa-utils TTL or the highest tier
  cap is ever raised above 90 days, this constant moves to the larger of the two, and the story that raises
  it owns that edit
- An integration test seeds an old-shape session, proves it still authenticates, refreshes it, and proves the
  successor is stored under a hashed key only — with every seeded key registered at creation and drained in
  `afterAll` (BCON-09)
**Traces:** NFR-AV01, NFR-AV02, NFR-MA01, NFR-MA02, NFR-MA05; BCON-01, BCON-02, BCON-08, BCON-09
**Evidence (gap):** no key-shape versioning exists

### E13-S03 — `INTROSPECTION_CODE` is compared in constant time   `built`
State plainly: the code is compared with `===` at two sites, and a mismatch's timing is proportional to how
many leading characters matched. The comparison must leak neither the content nor the length of the
configured code.
**domains:** backend, testing
**Acceptance criteria:**
- A `constantTimeEquals(a, b)` helper in `marketplace-common` has **no length comparison and no early return
  of any kind**. It HMACs both operands with a key produced once per process by `crypto.randomBytes(32)` and
  compares the two 32-byte digests with `crypto.timingSafeEqual`. Fixed-width digests satisfy
  `timingSafeEqual`'s equal-length requirement structurally, so the one-bit length leak is *removed* rather
  than padded around — padding is the weaker answer because a padding scheme has to be written correctly and
  can leak through its own boundary, while two digests are the same width for every input that exists.
  `grep -n 'length' <helper file>` returns nothing
- The HMAC key never leaves the process: not read from an env var, not logged, not exported, not written to
  Redis. A restart regenerates it, which is harmless because it is only ever compared against itself inside a
  single call. This is the double-HMAC construction, chosen over a bare digest so that an attacker who can
  submit candidate codes cannot precompute the digest they are racing against
- The helper uses `crypto.createHmac`, **not** `createHash` — E12-S11's acceptance criterion that
  `grep -rn "createHash" BEs/marketplace-common/src` returns exactly one hit stays true after this story lands,
  and a test asserts that count so the two stories cannot silently break each other
- **All six comparison sites** listed in §3 use it — three resource handlers, the logout handler **twice**, and
  the shared `resolveAuthorizationSession.mts:73` — and `grep -rn 'INTROSPECTION_CODE' BEs/*/src BEs/dev/*/src`
  shows no remaining `===` against it. Six, not two: an earlier draft of this story counted only the sites the
  audit happened to quote, and the logout handler's second check is the one most easily missed
- A missing header or an unset `INTROSPECTION_CODE` fails closed **through the same path**: the helper is
  still called, with an empty string standing in for the absent value, and returns `false`. No
  `if (!code) return false` guard sits in front of it, because such a guard reinstates the timing signal the
  story exists to remove
- Tests cover equal, different-same-length, different-length-shorter, different-length-longer, both-empty and
  one-empty; Stryker 100 with the equality and conditional mutants covered
- The epic records what constant-time comparison does **not** fix. Three things: the code is still accepted
  from anywhere the port is reachable, which is a topology problem routed to E13-S09; the bypass runs in every
  environment, which is E13-S11 and is the larger of the two fixes; and constant time on a JIT runtime is
  best-effort — this removes the algorithmic leak, not every microarchitectural one. Once E13-S11 lands the
  comparison no longer executes in production at all, which is why that story lands first. This one stays
  regardless: development machines are reachable too, and a gate whose failure mode is "the timing leak comes
  back" is not a gate worth relying on alone
**Traces:** NFR-SE01, NFR-SE02, NFR-SE06, NFR-SE12, NFR-MA01, NFR-MA02; BCON-01, BCON-02
**Evidence (defect):** plain `===` at the two sites above

### E13-S10 — The dual-read fallback is removed   `built`
**As a** platform, **when** 90 days have passed since the cutover and no old-shape key can still exist, **I
want** the fallback deleted **so that** the raw key shape stops being a supported way in.

> **Decision, 2026-08-10, platform owner: 90 days.** This story is the other half of E13-S02 and exists from
> the moment that one lands, rather than being remembered later. It is not a cleanup nicety — while the
> fallback stands, a raw session key is still a working credential, which is the exact property the epic
> exists to remove. Hashing the namespace does nothing for an attacker holding a dump taken before the
> cutover until this story lands.
>
> ⚠️ **Two conditions, not one.** The date is necessary and not sufficient: E13-S02's fallback-hit counter
> must have read zero across a full window as well. A non-zero count on day 90 does not mean sessions are
> old — it means something is still *writing* old-shape keys, which is a service that was never redeployed,
> and deleting the fallback would log its users out while hiding the real fault.

**domains:** backend, testing, documentation
**Acceptance criteria:**
- The raw-key read path, `DUAL_READ_REMOVE_AFTER`, the dated test guarding it and the fallback-hit counter
  are all deleted in one change — `grep -rn 'DUAL_READ_REMOVE_AFTER' BEs/` returns zero hits
- **The dual *delete* is reduced to one key, not left as two.** Deleting a key shape that can no longer
  exist is a second `del` per logout against a Redis cluster (BCON-08) for nothing, and it reads as though
  the cutover is still running
- The integration test that seeds an old-shape session and proves it authenticates (E13-S02) is **inverted,
  not deleted**: after this story an old-shape key must fail to authenticate, and a test asserting that is
  what stops the fallback being reintroduced by a later merge
- Both preconditions are recorded in the commit message: the cutover deploy date the constant was set from,
  and the observed counter reading. A story whose trigger is a date needs its evidence written where the
  next reader will look, and the epic is the wrong place — it will have been archived
- **`BGREWRITEAOF` is run again on every node, and this is the pass that finishes the job.** By now no
  old-shape key can be written and none can still be live — 90 days is the `REFRESH_TOKEN_EXPIRY` TTL — so the
  rewritten file contains digests and nothing else. The commit records the date of the run alongside the two
  preconditions. If any off-host backup of an AOF or `.rdb` predating the cutover is still retained (E13-S04
  asks whether one exists), the epic is not closed until its retention has been dealt with: a rewrite cannot
  reach a copy
- The `RISK_REGISTER` row E13-S02 opened is closed, naming this commit
- `yarn test:cov` stays 100/4 and `yarn test:mutation` stays 100 in `marketplace-common` and in every service
  that carried a fallback path
**Traces:** NFR-SE01, NFR-SE03, NFR-MA01, NFR-MA02, NFR-MA05; BCON-01, BCON-02, BCON-08

### E13-S11 — The introspection bypass is refused outside development   `built`
State plainly: `INTROSPECTION_CODE` is intended as a development-only convenience, and the code nowhere says
so. No comparison site consults `NODE_ENV`. The production hardening that exists gates something else — each
`index.mts:76-78` adds `NoSchemaIntrospectionCustomRule` and `depthLimit(10)` under `NODE_ENV === 'production'`,
which refuses the introspection **query** while the **authentication bypass** stays live. A production request
carrying no cookie and no `Authorization` header, only a matching header value, is admitted by
`authorizationLogoutHandler.mts:26-55` and by all three resource handlers. Making the intent true in code is a
larger security win than E13-S03's timing fix, and is close to free.
**domains:** backend, testing, documentation
**Acceptance criteria:**
- The bypass is gated by an **allowlist of environments, never a production denylist**: it applies only when
  `process.env.NODE_ENV` is exactly `development` or `test`, and every other value — unset, empty, `Production`,
  `staging`, a typo, a value injected by a broken deploy script — refuses. `NODE_ENV !== 'production'` is
  rejected in review as the wrong polarity: it fails **open** on precisely the input most likely to be wrong,
  and an unset variable is the common failure of every container runtime on the platform
- One shared predicate in `marketplace-common` decides this, exported and imported by all six sites, so the
  environment list exists once. `grep -rn "NODE_ENV" BEs/*/src BEs/dev/*/src` shows no second copy of the
  allowlist
- The gate is evaluated **before** the code comparison at every site, so outside `development` and `test` the
  configured value is never read. A test asserts this by stubbing `INTROSPECTION_CODE` and `NODE_ENV=production`
  together and proving the request is refused with the same error, and the same shape of error, as a request
  carrying no header at all — a caller must not be able to tell a wrong code from a disabled feature
- Behavioural tests per site, not one shared test: for each of the six, a request with the correct header and
  `NODE_ENV=production` is refused, and the refusal is the site's own existing error —
  `throwPreconditionFailedNoAuthCookie`, `throwPreconditionFailedNoAuthHeader` or
  `throwRefreshTokenExpiredOrDeleted` — rather than a new one that would itself identify the gate
- `INTROSPECTION_CODE` **stays** in every consuming service's `REQUIRED_ENV_VARS`. Removing it would be the
  natural tidy-up and is wrong here: the `${process.env.INTROSPECTION_CODE}` template literal stringifies an
  unset variable to the literal `'undefined'`, so a service that boots without it in a mislabelled environment
  hands the bypass to anyone who sends that word. Two independent things must both be wrong before the bypass
  opens, and the epic states that as the reason
- The `.env` templates and `SETUP.md` say what the variable is for and that it does nothing in production, so
  the next reader does not restore the old behaviour while debugging a staging box
- `yarn test:cov` stays 100/4 and `yarn test:mutation` stays 100 in `marketplace-common` and in each of the five
  services that carry a comparison site. ⚠️ The mutation gate is the real risk in this story: the environment
  comparison is a string literal, and a mutant that flips `'production'` to `''` must be killed by a test, not
  by a `Stryker disable` comment
**Traces:** NFR-SE01, NFR-SE02, NFR-SE06, NFR-SE12, NFR-MA01, NFR-MA02, NFR-MA05; BCON-01, BCON-02, BCON-05
**Evidence (defect):** no `NODE_ENV` check at any of the six sites listed in §3; the production hardening at
`index.mts:76-78` covers only the introspection query

## 5. Dependencies

- **E15 depends on E13-S01.** Hard ordering, stated in full in E15's §5: E15's account index stores session
  **key names**, and before E13-S01 those key names are the raw tokens. Building the index first would
  concentrate every live credential on the platform into one hash and make a dump strictly worse.
- **E14 depends on E13-S01 for the same reason.** E14's `family:` sets and `used:` tombstones are keyed on, and
  contain, session identifiers. Built before hashing, they are new raw-token structures — the exact thing this
  epic exists to remove.
- **Therefore E13-S01 and E13-S02 land first of all the session work**, ahead of E14 and E15. E12 is numbered
  ahead of this epic only because it is independent and near-free — nothing blocks on it. This deviates from
  the audit's own §6 suggested order, which put §3.3/§3.4 first; the deviation is deliberate and its reason is
  the two bullets above. E15-S01 (the broken logout) is the one thing that can and should land even earlier,
  since it touches no key shape.
- E13-S03 through E13-S09 depend on nothing and can land in any order.
- **E13-S03 depends on E13-S11, not the other way round.** Both touch the same six sites, and S11 is the story
  that removes the production exposure; S03 hardens what remains. Landing S03 first would spend the review on
  the smaller half. ⚠️ **S11's story number is higher than its landing position** — it was added on 2026-08-10,
  after the epic was drafted, and story ids are never renumbered once written down.
- **Landing order** (BCON-05, BCON-07):
  1. `marketplace-common` — the `NODE_ENV` allowlist predicate (E13-S11), `hashSessionToken`,

  4. `marketplace-dev-public-authorization` and the three `*-authenticated-authorization` services — hashed

  5. **`BGREWRITEAOF` on every Redis node**, once step 4 is fully rolled out and no old-shape writer remains.
     Production runs `appendonly yes`, so until this runs the cutover has changed the store and not the file
     on disk. Per node — a rewrite is local to the node that serves it.
  6. `docs/` — E13-S04 through E13-S09, the env template and `SETUP.md` lines E13-S11 owes, ADRs and the two

### What §7 said before, and why it changed

This section read *"Ten of eleven … the eleventh cannot land today by its own design"* from 2026-08-10 to
2026-08-14. That reading was right about the design and wrong about the premise it never stated: it treated
the 90-day window as a clock that had started. It had not. A window that drains deployed sessions does not
begin until something is deployed, and nothing on this platform ever has been. The gate was not waived —
it was found to be measuring an empty set, which is a different thing and is why it is written down here.

### The seventh comparison site — closed upstream, 2026-08-11

The out-of-scope site recorded in §2 and §3 is no longer a gap. **`@axiumine/koa-utils` 6.0.0** adds
`isIntrospectionBypassAllowed()` — the same allowlist, `development` or `test` and nothing else — exported
from `lib/isIntrospectionBypassAllowed`, and evaluates it as the **first statement** of
`verifyIntrospectionCode`, before `INTROSPECTION_CODE` is read at all. The gate sits in the primitive rather
than in the three middlewares that call it, so a direct caller cannot reach an ungated comparison. Against
5.9.0 the release is otherwise additive: no dependency, peer-dependency, engine or export removal, one new
`exports` key. It is a major because the behaviour break is real — a consumer running the bypass under
`staging` or an unset `NODE_ENV` loses it, which is the point.

All ten consuming repos here are on `^6.0.0` as of 2026-08-11 — `marketplace-common` and the nine services,
`package.json` and `yarn.lock` in each, `./deploy-local.sh` re-run. Every build passes and `yarn test:cov`
stays 100/4 in all ten.

⚠️ **This changed nothing at runtime on this platform, and that is the expected result.** No service mounts
the koa-utils handlers for this check — each has its own, and `grep -rn "koa-utils/koa/middleware"` across
`BEs/*/src` finds only `verifySignedRefreshToken`. `verifyIntrospectionCode` is called from nowhere in this
workspace's `src/`. The six sites were already gated by `E13-S11`; 6.0.0 closes the hole for the **next**
consumer, and stops a service that later swaps its handler for the published one from silently reopening
what this epic closed.

Two things the bump did **not** settle, both open:

- `marketplace-common/src/others/isIntrospectionBypassAllowed.mts` is now a byte-equivalent copy of the
  package's export. Converging on one definition touches the `exports` map, the unit suite and the mutation
  gate, so it is a change of its own, not a side effect of this one.
- `marketplace-common`'s peer range for the package is `"*"`, which a consumer can still satisfy with 5.9.0
  and get the ungated comparison back. Tightening it to `>=6` costs a `marketplace-common` major.
